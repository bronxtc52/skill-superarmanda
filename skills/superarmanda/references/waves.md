# Waves: большая задача цепочкой свежих сессий

Режим растягивает конвейер superarmanda на цепочку волн. Волна — юнит superarmanda:
одна фича, один PR, полный конвейер шагов 3–7. Между волнами работу несёт диспетчер
со свежим контекстом. **superarmanda отвечает за качество внутри волны, диспетчер — за
поток между волнами.** Волна заканчивается проверенным PR и сама не мерджит.

Вход только явный: `/superarmanda --waves <задача>` (фаза A),
`/superarmanda --wave <id> --plan <path>/waves.json` (старт волны) и
`/superarmanda --wave <id> --resume` (продолжение после `/clear`). Режим не включается
сам, даже если задача большая. Без этих флагов skill работает как v0.6.0.

Цепочка строго последовательная: одна волна, один coder. Параллельных волн нет.
Профили ролей, внешний reviewer, правила `fix-loop` и PR-гейт не меняются.

## Фаза A — текущая сессия

1. Шаги 1–2 superarmanda как обычно: требования, приёмка, риск, base, проверки, профили.
2. Разбиение на волны. Каждая волна — цель, «Готово, когда», класс риска, проверки с
   командами, зависимости. Класс риска волны — нижняя граница для всех её задач: `state.py init
   --from-plan` записывает его в `review_policy.level` manifest, и от него зависят модель coder и
   tester и число ревью (при `high` — coder на Opus и два ревью, Astra и Fable; [profiles.md](profiles.md),
   «Модель роли по риску»). Правило: задачи про безопасность и маскировку обязаны иметь `risk: high` — волна
   с такой задачей планируется как `high`, либо риск самой задачи поднимает `state.py task-risk`. Последняя волна плана — «Релиз»: сквозная приёмка всей
   цепочки. Она входит в одобряемый `waves.json` как обычная волна, иначе её нельзя
   запустить через `--plan`. Как любая волна, она проходит шаги 3–7 и даёт PR, поэтому
   в её требованиях обязано стоять конкретное изменение в репозитории: сквозной тест
   приёмки, версия, release notes. Волна «Релиз» без изменения в коде не планируется.
   Результат — `waves.json` и человекочитаемый `wave-plan.md`.
   Имя цепочки (`chain` в `chain.json`), id волн и `tmux_prefix` выбираются по смыслу работы (`waves-tails`, `W2`, `fp-`), без персональных данных и данных задачи (имён людей, клиентов и пациентов, адресов, номеров): они входят в каждое внешнее уведомление, в имя tmux-сессии и в дашборд, а в именованном виде попадают в Telegram.
3. Внешний review плана волн по [review-contract.md](review-contract.md) — **всегда,
   при любом классе риска**, и **двумя ревьюерами**: Astra (`--profile claude-host`) и Fable
   (`--profile codex-host`) по одному пакету. Ошибка разбиения размножается на все волны.
   Fable зовётся не больше `plan_review_fable_rounds` кругов (по умолчанию 2); каждый круг
   копируется в `plan-review/history/`, дальше план одобряет Astra (раздел ниже).
   Оба результата сохраняются в каталоге прогона, в `<run_dir>/plan-review/`, вместе с пакетом
   и хешем одобренного плана; `wab.py launch` новой цепочки без них отказывает (раздел
   «Ревью плана: `plan-review/`» ниже).
4. Предполётный чек-лист владельцу одним списком: human-only шаги, мандат, форма сдачи
   (см. ниже).
5. «Ок» владельца закрывает `waves.json`, `wave-plan.md` и `mandate.md`. Одобренный
   `waves.json` кладётся в каталог прогона, `<run_dir>/waves.json`, вне любых worktree:
   волны стартуют на свежем `origin/<base_branch>`, где файла из worktree фазы A нет,
   а копия внутри рабочей копии волны сделала бы её дерево грязным. Во все волны
   передаётся абсолютный путь к этому файлу.
6. Запуск диспетчера. Координатор фазы A на этом заканчивает и сам волны не ведёт.

### Ревью плана: `plan-review/`

План ревьюят оба ревьюера, и это проверяет машина, а не слово координатора (#86 п.3). Пакет
собирается как для обычного ревью: одобряемый `waves.json` (и `wave-plan.md`) коммитятся во
временный git-репозиторий, `review.py packet` строит пакет, чей diff **добавляет** файл
`waves.json` в корне, затем `review.py run` запускается на этом пакете с `--profile claude-host`
и с `--profile codex-host`. Круги правок плана повторяют это с новым пакетом. **Каждый круг
копируется в `plan-review/history/`**: пакет круга (`packet-rN.json`) и отчёт Fable этого круга
(например `rN-codex-host.json`), обычными файлами, не симлинками; без пакета рядом круг Fable не
засчитывается (ниже). После «ок» владельца в каталоге прогона лежит результат ПОСЛЕДНЕГО круга:

| Файл в `<run_dir>/plan-review/` | Что это |
|---|---|
| `plan.sha256` | sha256 одобренного `waves.json`, одна строка: голый хеш (64 hex-символа в нижнем регистре) или строка `sha256sum waves.json` (`<hex>  waves.json`, берётся первое поле); равен `plan_sha256` в `chain.json` |
| `packet.json` | пакет `review.py packet`; его diff добавляет `waves.json` с этим же sha256 |
| `result-claude-host.json` | отчёт `review.py run --profile claude-host` (Astra) по этому пакету, `gate_ready: true` |
| `result-codex-host.json` | отчёт `review.py run --profile codex-host` (Fable) по этому пакету, `gate_ready: true`; может отсутствовать после исчерпания кругов Fable (1.4.0, ниже) |
| `result-codex-host-opus.json` | только для запасного маршрута: отчёт `--profile codex-host-opus` с `gate_ready: true`; засчитывается, когда `result-codex-host.json` — отчёт ошибки квоты Fable (`status: error`, `error_category: quota`) того же пакета |
| `history/` | 1.4.0: копии кругов ревью плана — пакет `packet-rN.json` и отчёт Fable каждого круга; нужен маршруту «только Astra» |
| `architect.md` | отчёт архитектора (`architect`, модель политики) фазы A: ТЗ, план задач, риски, команды проверок; `launch` его не проверяет, запись `task-result` в режиме волн не требуется (1.2.4) |

`wab.py launch` первой волны новой цепочки (в прогоне ещё не запускалась ни одна волна)
проверяет: в `chain.json` есть `plan_sha256`; `plan.sha256` равен ему; `packet.json` — целый
пакет `review.py` (хеш совпадает с содержимым), и его diff добавляет `waves.json` с sha256,
равным `plan_sha256`; оба отчёта — отчёты своих профилей (модели сверяются по таблице
`review.py`, как у ревью задачи), со статусом `pass` и `gate_ready: true`, а их
`state_packet_hash` равен хешу этого пакета. Любое расхождение — отказ запуска с причиной
(`launch refused: plan review: …`, событие в `events.log`), волна не стартует. Как текущие
отчёты читаются только эти имена файлов: результаты прошлых кругов плана вместо текущих не
засчитывается, а отчёт прошлого круга, положенный под нужным именем, отличается по
`state_packet_hash`; `history/` читает только маршрут «только Astra» ниже. Новая цепочка без `plan_sha256` в `chain.json` тоже получает отказ:
ревью плана не к чему привязать. `plan-review/` — настоящий каталог внутри каталога прогона, не симлинк
(как и файлы в нём): симлинк — отказ.

**Fable не больше N кругов, дальше решает Astra (1.4.0, #108).** Решение владельца: ревью плана с
Fable может не сходиться (15 кругов в `waves-fable-policy`), поэтому после `plan_review_fable_rounds`
кругов Fable (поле `chain.json`, по умолчанию 2) план одобряет Astra. Если `result-codex-host.json`
и `result-codex-host-opus.json` в `plan-review/` нет, `launch` принимает план, когда:

- `result-claude-host.json` — `pass` с `gate_ready: true` на текущем пакете и с `created_at`
  (поле отчёта `review.py` с 1.4.0, UTC; [review-contract.md](review-contract.md));
- в `history/` не меньше N кругов Fable. Круг — отчёт профиля `codex-host` со статусом `findings`,
  моделями Fable, `capabilities.primary_model_verified: true` и `created_at` в UTC, чей пакет лежит
  в `history/` же: целый пакет `review.py`, diff которого добавляет `waves.json`, а `reviewed_head`
  отчёта равен HEAD пакета. Круги считаются по РАЗНЫМ пакетам; отчёты ошибки (в том числе квоты),
  `pass` и отчёты Astra кругами не считаются, `gate_ready` с круга не спрашивается (`review.py`
  пишет `false` у любого `findings`);
- **Astra новее Fable:** `created_at` отчёта Astra позже каждого валидного отчёта Fable в `history/`
  с `created_at` при любом статусе (`pass`, `findings`, `error`/quota; засчитан он кругом или нет —
  пакет нужен только для зачёта круга; отчёт без `created_at` не круг и в порядке не участвует) — находки
  последнего круга разобраны правкой плана, и эту правку проверила Astra. Круг не старше Astra —
  отказ;
- в `history/` нет `findings` Fable на САМОМ одобренном пакете: такие находки никто не разбирал —
  отказ.

Неразобранные по существу находки последнего круга Fable — обязанность координатора; машина
проверяет только порядок и число кругов. Успех пишет в `events.log` `plan review: Fable rounds
exhausted (N), Astra-only pass accepted; last Fable report: plan-review/history/<файл>`. Модель угроз
прежняя: файлы кладёт координатор цепочки, проверка защищает от ошибки, а не от подделки.
Если `result-codex-host.json` есть, действуют прежние правила (он обязан быть `pass` либо
закрыт запасным Opus по квоте). **Принятое ограничение:** оставшийся в `plan-review/`
`result-codex-host-opus.json` выключает маршрут «только Astra» — отказ (fail-closed) с неочевидным
текстом про quota evidence; если круги Fable исчерпаны, убери этот файл.

Проверка идёт только в `launch` новой цепочки. Уже запущенная цепочка — повторный `watch`,
запуск следующей волны диспетчером или координатором, перезапуск остановленной волны — на
`plan-review/` не проверяется: цепочка, начатая на версии до 1.2.2, доходит до конца без него.

### Схема `waves.json` v1

```json
{
  "version": 1,
  "chain": "<имя цепочки>",
  "repo": "owner/name",
  "base_branch": "main",
  "waves": [
    {
      "id": "W1",
      "title": "...",
      "goal": "...",
      "requirements": "...",
      "acceptance": ["..."],
      "risk": "low | medium | high",
      "checks": [{"name": "unit", "cmd": "..."}],
      "depends_on": []
    }
  ]
}
```

Схема строгая, её проверяет `state.py init --from-plan`. `id` уникален, из
`[A-Za-z0-9._-]+`, не `.` и не `..`. Каждый элемент `depends_on` называет ровно одну
более раннюю волну. Отказ без создания manifest: лишние или дублирующиеся ключи, неверный
тип, пустая строка, ссылка вперёд или на себя, одиночный суррогат, симлинк или не обычный
файл, файл больше 1 MiB. Конкретного base SHA в плане нет: он появляется только после
мерджа предыдущей волны и передаётся в `init` через `--base`.

### Предполётный чек-лист

Владельца в боевом прогоне звали 6–7 раз за волну, почти всегда ради мерджа, выката,
секрета или приёмки. Поэтому эти шаги называются заранее, одним списком. Какие из них
волна может сделать сама, а какие host ей запрещает, определяют права и policy
конкретного host; чек-лист спрашивает о том, что есть на этом host, и не предполагает
конкретных механизмов:

- **мердж** каждой волны сразу в базовую ветку, stacked PR не используются;
- **выкат и доступ к проду** — разрешены ли волне, и если нет, кто и как их делает;
- **секреты** — где они хранятся и кто их записывает. Если волне запись запрещена, она
  готовит команду или скрипт, а выполняет его владелец;
- **приёмка** — что владелец проверит руками и в какой момент;
- доступы, внешние панели, материалы, решения вне кода;
- форма сдачи и критерий «готово» для каждой волны и для цепочки;
- **имя цепочки, id волн и `tmux_prefix`** выбраны по смыслу работы, без персональных данных и данных задачи: они уходят в Telegram, в имя tmux-сессии и в `ATTENTION`; внешние уведомления собираются из шаблонов без свободного текста волны, а первая строка вопроса волны добавляется только если владелец осознанно включил `"telegram_quote": true` (для репозитория без PII/PHI);
- **модель координатора** волн: без поля `model` новая цепочка (1.4.0) запускает волны на Opus
  (`claude-opus-5-5`); другая модель (например Fable) — осознанное решение владельца. Модели ролей
  внутри волны задаёт политика ролей; поднять её можно полем `role_models` ([profiles.md](profiles.md));
- **остаток Fable**: `python3 scripts/waves/fable_usage.py` (локальный расход этой машины за сутки
  и 7 дней в единицах 1M взвешенных токенов, порог 80% бюджета) и claude.ai/settings/usage
  (общий лимит подписки, видит все машины). Fable в цепочке нужна ревью плана и вторым ревью
  задач high; при остатке на исходе — решение владельца до запуска;
- **политика решений и потолок прогонов**: какие развилки диспетчер закрывает сам и каким ответом.
  Дефолт фазы A по решению владельца 2026-10-05 — `answer: invariant` на `needs_decision` и
  `blocked_cap` («доделай как следует»), `max_runs: 5` (до пяти прогонов на волну) и к ним
  `max_auto_answers: 10` (по умолчанию 3 — автоответы кончились бы раньше прогонов); подробно —
  «Рекомендуемая конфигурация фазы A» в разделе «Политика решений». Другая политика или другой
  потолок — осознанное решение владельца. Красная зона, `merge_gate` и `plan_mismatch` в любом
  случае идут владельцу;
- **ревью плана двумя ревьюерами**: в `<run_dir>/plan-review/` лежат пакет, `plan.sha256` и отчёты
  `claude-host` и `codex-host` с `gate_ready: true` по пакету одобренного плана либо, после
  `plan_review_fable_rounds` кругов Fable в `plan-review/history/`, `pass` Astra новее последнего
  круга (раздел «Ревью плана: `plan-review/`»); без них `launch` новой цепочки откажет;
- **версия скилла на время цепочки**: установленный скилл обновляется только между волнами, до
  старта следующей. Волна, начатая на старой версии, доводится на ней или перезапускается новым
  прогоном (`state.py init` на новой версии) — правила гейта для high-волны manifest старой
  версии не пройдёт;
- допуск репозитория цепочки к автономной работе — только если host policy требует
  admission (см. [workflow.md](workflow.md) и «Admission» в разделе `chain.json` ниже). Тогда
  условия допуска задаёт host, и отказ admission останавливает фазу B. На unmanaged host без такой policy волна работает в
  обычном изолированном Git worktree, и этот пункт помечается «не требуется».

Чего не нужно, помечай «не требуется». Не запускай фазу B, пока список не закрыт.

### Мандат

Мандат — что владелец разрешил диспетчеру и волнам без повторного вопроса: мердж при
пройденном гейте, выкат, создание Sentry-проекта, установка на хосте, запись секретов.
**Удаление данных, платные ресурсы и DNS в мандат не входят никогда** и всегда идут через
`BLOCKED`.

- Мандат живёт только в `<run_dir>/mandate.md`, где `run_dir` = `runs/<chain>/<run_id>/`.
  Первая строка — `Прогон: <run_id>`, иначе мандат игнорируется. В общий протокол волны
  мандат не пишется: датированный мандат одного прогона не должен доехать до другого.
- Одобренные байты пинятся полем `mandate_sha256` в `chain.json` вне `run_dir`: волна
  может писать в каталог прогона, а пин — нет. Не совпал хеш — волна не запускается.
  Если ключ `mandate_sha256` есть, его значение — ровно 64 hex-символа в нижнем регистре;
  `""`, `null`, `false`, `0` и любой другой формат — отказ `load_chain`, а не «пина нет».
  Без пина ключ просто не пишется. При заданном пине отсутствующий, пустой или с чужой
  первой строкой `mandate.md` — тоже отказ запуска, а не тихий откат к одному общему
  протоколу. Нечитаемый `mandate.md` (каталог, нет прав) — отказ с причиной и с пином, и без.
- Кто физически пишет `mandate.md`, решает host. Если права хоста не дают агенту
  записать инструкцию для других сессий, файл пишет владелец сам или выдаёт разрешение
  средствами своего хоста; конкретные правила прав живут в интеграции хоста, а не в
  skill. Фаза A проверяет, что `mandate.md` записан и его хеш запинен, до старта фазы B.
- Действие, в котором волне отказали права host, за неё не выполняется другим путём. Это
  обход разрешений.
- Обновление установленного скилла посреди цепочки — только между волнами: после мерджа одной
  волны и до старта следующей. Если мандат разрешает обновление, он называет этот момент;
  обновлять скилл под работающей волной нельзя: её manifest создан по правилам старой версии, а
  гейт мерджа судит по правилам новой.
- Политику решений диспетчер читает только из `chain.json` (раздел ниже), но мандат называет её
  волнам и владельцу теми же словами, что и ответ диспетчера. Образец строк `mandate.md` для
  рекомендуемой конфигурации (`answer: invariant`, `max_runs: 5`, `max_auto_answers: 10`):

  ```text
  Политика решений: на развилки needs_decision и blocked_cap ответ — доделай как следует:
  ещё один круг или прогон, чини класс находки целиком, не латай; находки low/P3 —
  fix-loop --defer в остаток.
  Потолок: 5 прогонов на волну и 10 автоответов на волну. Выше потолка, при внешнем сбое и в
  красной зоне решает владелец.
  ```

### Политика решений

Политика решений живёт **только в `chain.json`**, в поле `decision_policy`: список развилок, на
которые диспетчер отвечает сам, без владельца. В `mandate.md` политика не разбирается: заголовок
«Политика решений» там — обычный текст мандата, не правило и не ошибка.

```json
"decision_policy": [
  {"class": "needs_decision"},
  {"class": "blocked_cap", "rec": "new_run"},
  {"class": "question", "rec": "A"}
]
```

- Ключи только `class`, `rec` и `answer`. `class` — `needs_decision`, `blocked_cap`, `question`; `rec`
  (необязательно) — конкретный вариант из метки волны, `[A-Za-z0-9_.-]{1,40}`. Без `rec` правило
  разрешает любой рекомендованный вариант этого класса. Решает первое по порядку списка правило,
  подходящее по `class` и `rec`; следующие не рассматриваются, даже если это правило ответа не дало.
- `answer` (необязательно; 1.2.5, [#89](https://github.com/bronxtc52/skill-superarmanda/issues/89)) — фиксированный
  вариант ответа диспетчера: он уходит волне, какой бы `rec` она ни назвала. Словарь закрытый и
  зависит от класса: `needs_decision` — `invariant`, `cut_surface`, `accept_limitation`;
  `blocked_cap` — `invariant`, `new_run`, `accept_limitation`. У `question` варианты свободные,
  `answer` с ним не допускается. Правило без `answer` работает как в 1.2.0: ответ «по рекомендации
  волны», без машинной проверки и без новых полей `state.json`.
- Проверка строгая, в `load_chain`: не список, не объект, лишний ключ, неизвестный класс, ключ
  `red`, `merge_gate`, `plan_mismatch`, неверный `rec`, `answer` вне словаря своего класса или при
  `question` — отказ `chain.json: decision_policy …`. Нет поля (или пустой список) — автоответов нет.
- Поле входит в идентичность прогона (не tunable): правка между `launch` и `watch` — отказ входа
  координатора. `chain.json` лежит вне `run_dir` (это проверяет `load_chain`), волна его не
  перепишет.
- Красной зоны в политике нет и быть не может: `red=yes` в метке всегда идёт к владельцу, как и
  `merge_gate` (эту метку пишет только диспетчер) и строка без метки.
- `plan_mismatch` в политику не входит: поправка одобренного `waves.json` требует «ок» владельца и
  нового `plan_sha256` (раздел «Старт»), автоответ её не даёт. Метка `class=plan_mismatch`
  допустима, но такая развилка всегда идёт владельцу.

**Автоответ.** В такте `watch` на новый эпизод `BLOCKED` с разобранной меткой, `red=no`, классом
(и `rec`, если правило его называет), разрешённым политикой, и классом не `merge_gate` диспетчер
пишет в окно волны тем же путём, что `say` (`_InputLock`, проверка отправки, повтор только Enter):
`[wab] РЕШЕНИЕ ПО ПОЛИТИКЕ (chain.json): вариант <rec>. Действуй по своей рекомендации, затем
запиши RUNNING в status. Находки low/P3 — fix-loop --defer в остаток.` Затем строка в
`<run_dir>/<волна>/policy-decisions.log` (время UTC, класс, `rec`, первая строка вопроса после
`safe_text()`), событие `<волна>: policy auto-answer: class=… rec=…` и уведомление `policy_answer`:
оно информирует и ответа не ждёт (сигнала ATTENTION не открывает); его эпизод кончается сменой
статуса волны. Отметка «уже отвечено» стоит на эпизод: повторный такт той же строки `BLOCKED` не
отвечает второй раз. Прямо перед вводом (и ещё раз под замком ввода) диспетчер перечитывает `status`: строка сменилась (владелец
ответил в окне, волна записала `RUNNING` или новую развилку) — ничего не шлёт, следующий такт
разбирает новый эпизод. Доставка не удалась (`NotSubmitted`, ввод занят `say`) — уходит обычное
уведомление `BLOCKED`, следующий такт пробует снова; успешный повтор снимает этот сигнал
`blocked` (и ATTENTION) — ответа владельца он больше не ждёт.

**Предохранитель.** Не больше `max_auto_answers` автоответов на волну — считаются все попытки
волны, перезапуск счётчик не сбрасывает; ответ, начатый, но не засчитанный (окно или `watch` умерли
между вводом и сохранением счётчика), тоже засчитывается (`chain.json`, по умолчанию 3, `0` — автоответов нет, настраивается на лету). Дальше — обычный `BLOCKED`
владельцу и одно событие `policy cap reached`.

**Фиксированный ответ (`answer`).** Правило с `answer` шлёт в окно волны текст диспетчера со смыслом
варианта: `[wab] РЕШЕНИЕ ПО ПОЛИТИКЕ (chain.json): вариант <answer>.`, затем:

- `invariant`, новый прогон не нужен — «Доделай как следует: ещё один круг, чини класс находки
  целиком, не латай; находки low/P3 — fix-loop --defer в остаток. Решение запиши: fix-loop
  --decision invariant.»;
- `invariant` или `new_run`, нужен новый прогон — «Доделай как следует: чини класс находки целиком,
  не латай; находки low/P3 — fix-loop --defer в остаток.» (у класса `needs_decision` затем то же
  «Решение запиши: fix-loop --decision invariant.»);
- `cut_surface` — «Вырежи поверхность, давшую находку (fix-loop --decision cut_surface), остаток — в
  result.md.»;
- `accept_limitation` у класса `needs_decision` — «Прими ограничение (fix-loop --decision
  accept_limitation): строка в «Принятые ограничения» PR и в остаток.»;
- `accept_limitation` у класса `blocked_cap` — «Прими ограничение: открой новый прогон (state.py
  init --from-plan на новом пути), прогон <n> из <max>, и в нём находку не чини, а прими как
  ограничение (fix-loop --accept, строка в «Принятые ограничения» PR и в остаток).».

Ответ называет только то, что волна может исполнить в состоянии развилки, и одно решение.
`fix-loop --decision` `state.py` принимает только у задачи `needs_decision`, поэтому команда названа
только в ответах этого класса. Заблокированная задача (`blocked_cap`) в своём прогоне не закончится:
любой ответ этого класса открывает новый прогон, а ограничение в нём принимается через
`fix-loop --accept`.

Когда нужен новый прогон, к тексту варианта добавляется «Открой новый прогон (state.py init
--from-plan на новом пути), прогон <n> из <max>.» (у `blocked_cap` с `accept_limitation` новый прогон
уже назван в самом тексте); если рекомендация волны отличается от `answer`,
она названа в скобках: «(рекомендация волны: <rec>)». В конце — «Затем запиши RUNNING в status.»
Новый прогон нужен, когда класс развилки `blocked_cap` (при любом `answer`) или счётчик `fix_cycles`
задачи не меньше 3 (кап кругов `state.py`). Строка `policy-decisions.log`, событие и уведомление
правила с `answer` называют и вариант, и рекомендацию волны: `<время UTC> class=<класс>
answer=<вариант> rec=<rec> <первая строка вопроса>`, событие `<волна>: policy auto-answer: class=…
answer=… rec=…`; уведомление `policy_answer` словами шаблона (с 1.2.7): «Тип вопроса: <класс словами>;
выбрано: <вариант словами>» (рекомендация волны — только в журнале и событии). У
правила без `answer` формат журнала прежний: `class=… rec=…`.

**Машинная проверка.** Перед фиксированным ответом — при любом значении `answer` — диспетчер
проверяет развилку по своим файлам, не по тексту волны. По порядку:

1. manifest текущего прогона (`wab.current_manifest`) найден, читается и проходит схему `state.py`;
   `runs.json` волны с `answer` обязателен (запасной путь к стандартному manifest здесь не
   засчитывается), не пуст, и `run.index` manifest совпадает с индексом последней записи `runs.json`;
2. в manifest ровно одна задача в статусе класса: `needs_decision` для класса `needs_decision`,
   `blocked` для `blocked_cap`;
3. у задачи `needs_decision` есть источник fix-loop — `decision_required_for`;
4. нет внешнего сбоя: ни у одной роли готовности этой задачи (`coder`, `tester`,
   `cross_provider_reviewer`, `second_reviewer`, `internal_reviewer`, `final_check`,
   `github_codex_review`) текущий результат (записанный на `head` manifest) не имеет статуса
   `unavailable` или `error`. Внешний сбой ещё одним кругом или прогоном не чинится — решает
   владелец. Fable-ревью, закрытое засчитанным `codex-host-opus`, сбоем не считается: текущий
   результат роли тогда — `pass` или `findings`;
5. если нужен новый прогон — и только тогда — индекс текущего прогона меньше `max_runs` (живое
   значение `chain.json`); иначе потолок прогонов исчерпан;
6. ключ развилки — волна, `run_id`, индекс прогона, задача, класс, источник — ещё не получал
   автоответа. Ключи хранятся в `state.json` в записи волны: отвеченные — в `policy_keys`, ответ в
   полёте — в `policy_key_pending` вместе с его текстом; они переживают перезапуск `watch` и
   перезапуск волны. Повтор только Enter текст заново не печатает, но проверку проходит целиком
   ещё раз (свой ключ в полёте повтором не считается): Enter дожимается, только если она проходит
   сейчас и даёт тот же ключ и тот же текст. Иначе это отказ эпизода с причиной «состояние развилки
   изменилось после ввода ответа: …» — напечатанный текст убирается из поля ввода, ответ
   засчитывается в кап, ключ переносится в `policy_keys`. Ключ в полёте не
   теряется: если напечатанный ответ брошен (строка `status` сменилась, ответил владелец, окно
   закрывается) и мог уйти в окно, ключ переносится в `policy_keys` — развилка считается
   отвеченной, в том числе когда следующим срабатывает правило без `answer`. Та же развилка того же
   прогона второй раз идёт владельцу. Испорченная отметка в любой записи волны, текущей или
   архивной (`policy_keys` не список списков, `policy_key_pending` не объект с ключом-списком,
   сам список `attempts` не список объектов), — отказ с причиной «отметки автоответов в state.json
   испорчены», а не «ничего не отвечено».

Любой сбой разбора — тоже отказ, а не падение такта. Отказ проверки ведёт эпизод обычным путём
`BLOCKED` к владельцу: одно событие на эпизод `<волна>: policy answer not sent: <причина>` и строка
«Автоответ по политике не отправлен» в уведомлении `BLOCKED` (с 1.2.7 без причины: она только в событии). Причина — фиксированная
формулировка диспетчера с именем задачи или роли из manifest и числами. Кап `max_auto_answers`
отказ не тратит (исчерпанный кап проверяется раньше и даёт своё событие `policy cap reached`).
Машинный отказ окончателен для эпизода. Эпизод — та же строка `status` и тот же штамп файла; отметка
отказа `policy_refusal` лежит в записи волны в `state.json` и переживает перезапуск `watch`. На
следующих тактах проверка не повторяется и автоответа нет, даже если причина исчезла (владелец
поднял `max_runs`, появился `runs.json`): владельца уже спросили, и отвечает он — в окне волны или
через `wab.py say`. Строка, записанная заново (другой штамп), или другая строка — новый эпизод, он
решается заново. Новый эпизод той же строки после автоответа или отказа, оставшийся без автоответа
(снова отказ, исчерпанный кап), идёт владельцу своим уведомлением `BLOCKED`: под правилом с `answer`
отметка уведомления принадлежит эпизоду, а не тексту строки, и волна не ждёт молча. Один лишь другой штамп эпизод не меняет: пока файл `status` пуст или не читается
(волна переписывает его, такт решает по последней известной строке), отказ остаётся и второго
события нет. Отметка снимается, когда эпизод кончился; испорченная отметка — не объект или объект
с испорченными полями — читается как отказ.

**Рекомендуемая конфигурация фазы A.** По решению владельца 2026-10-05 фаза A по умолчанию пишет в
`chain.json` политику «доделай как следует» и потолок пяти прогонов на волну:

```json
"decision_policy": [
  {"class": "needs_decision", "answer": "invariant"},
  {"class": "blocked_cap", "answer": "invariant"}
],
"max_runs": 5,
"max_auto_answers": 10
```

На развилку двух кругов волна получает ещё один круг, на исчерпанный кап кругов — новый прогон, пока
прогонов меньше пяти (без поля `max_runs` потолок — 2). `max_auto_answers` — независимый
предохранитель (по умолчанию 3): с пятью прогонами автоответы кончились бы раньше прогонов, поэтому
к этой конфигурации рекомендовано `"max_auto_answers": 10` — до двух автоответов на прогон (развилка
двух кругов и исчерпанный кап кругов). `question` в этой политике нет: такие
развилки идут владельцу. Другой набор правил или другой потолок — осознанное решение владельца;
фаза A называет политику в предполётном чек-листе и строками `mandate.md` (образец — в разделе
«Мандат»).

**Ответ владельца и автоответ ([#51](https://github.com/bronxtc52/skill-superarmanda/issues/51)).**
`wab.py say` в момент, когда текст попал в окно (`on_typed`, под `_InputLock`; даже если Enter потом не
прошёл), атомарно пишет маркер `<run_dir>/<волна>/owner-answered`: JSON `{"status": <строка status>,
"stamp": [inode, mtime_ns файла status], "at": <UTC>}` (tmp-файл в том же каталоге, `fsync`,
`os.replace`, `fsync` каталога). `say` по-прежнему не пишет `state.json` и не берёт замок прогона.
`watch` читает маркер до капа и ещё раз под замком ввода: совпали строка `status` И штамп —
эпизод отвечен владельцем (строка и штамп снимаются одним снимком stamp → чтение → stamp; если файл
перезаписан между ними, штамп маркера `null`, событие, маркер не совпадёт ни с каким эпизодом), автоответ не печатается, кап не тратится, одно событие `policy answer not
sent: the owner answered this episode (say)` на эпизод, уведомление `BLOCKED` по нему не поднимается.
Та же строка в переписанном файле (другой штамп) — новый эпизод, маркер не действует. Нет маркера,
битый или нечитаемый — как «маркера нет». Висящий автоответ (`pending_enter == "policy answer"`) при
совпавшем маркере очищается из поля ввода и засчитывается в кап (мог уйти).

**Очистка поля ввода ([#48](https://github.com/bronxtc52/skill-superarmanda/issues/48),
[#31](https://github.com/bronxtc52/skill-superarmanda/issues/31),
[#50](https://github.com/bronxtc52/skill-superarmanda/issues/50),
[#53](https://github.com/bronxtc52/skill-superarmanda/issues/53)).** Набранный, но не отправленный
текст диспетчера (`pending_enter`) не снимается молча: его судьба решается в одном месте
(`_abandon_input`). Случаи: устаревший будильник (PR закрыт или HEAD сменился, #31 — сверка PR/HEAD идёт
ДО повторного Enter, без дросселя опроса), провал гейта нового эпизода, смена статуса волны, автоответ,
у которого сняли кап на ходу (#50) или чей `precheck` под замком ввода провалился на Enter-only повторе
(#53; ответ засчитывается в кап). Факт переносится в резерв `pending_clear` (`what`, `why`), затем поле
очищается. «Ввод пуст» читается только с экрана `capture-pane -p -e`: после `❯` и на строках
продолжения до нижней рамки остаётся лишь пробел/NBSP или dim-текст (серая подсказка `Try "…"`;
без `-e` она неотличима от набранного), и нет футера `paste again to expand` (после очистки свёрнутой
вставки он держится ещё секунды — ждём без клавиш, до ~15 с). Круг очистки — `C-e C-u C-k BSpace`, до
4 кругов со снимком `-e` после каждого. Нет рамки ввода (на экране диалог) — клавиш не шлём. Успех
только по экрану: событие `input cleared: <что> (<причина>)`, резерв снят. Провал — резерв остаётся,
одно событие `input NOT cleared: <что>: <причина>` на эпизод, следующий такт повторяет очистку; пока
резерв висит, диспетчер ничего не печатает в это окно, а `say` отказывает так же, как при
`pending_enter`. Окно закрыто — резерв снимается без клавиш.

Закрытие окна (`/exit` после `DONE`/слияния) идёт тем же путём: под `_InputLock`, и только в пустое
поле. Висящий `pending_enter` или `pending_clear` сначала очищается; поле, не пустое по экрану, —
тоже. Не очистилось — `/exit` не отправлен, событие `/exit not sent: <причина>`, намерение
`pending_exit` остаётся, повтор в следующем такте. Экран без рамки ввода (диалог доверия/разрешения, пустой
capture после сбоя `capture-pane`) `/exit` блокирует: Enter мог бы нажать кнопку диалога. `/exit` не
отправлен, `pending_exit` остаётся, событие `/exit not sent: no input box on the screen` — одно на эпизод. «Dim» в SGR — только самостоятельный параметр `2`; двойка внутри составного
цвета (`38;5;2`, `38;2;r;2;b`, `38:2::…`) — не dim, при сомнении ввод считается непустым.

### Пин плана

`init --from-plan` записывает в manifest `plan.sha256` — хеш файла **на момент старта
волны**. Это не доказательство одобрения: правку поздней волны после «ок» он не поймает.
Пин (реализован, W5): хеш одобренного `waves.json` лежит в `chain.json` как
`plan_sha256`; диспетчер сверяет его перед запуском каждой волны (до клона и записи
`STARTING`) и при расхождении отказывает: `BLOCKED: plan changed since approval`.
Диспетчер отдаёт хеш сессии волны в `WAB_PLAN_SHA256`, а
`init --from-plan --expect-sha256 <hex>` без совпадения manifest не создаёт. С 1.2.2 пин
обязателен для новой цепочки: к нему привязаны ревью плана (`plan-review/`) и риск волны в
гейте мерджа; `launch` первой волны без `plan_sha256` отказывает. В цепочке, запущенной до 1.2.2, без пина
фаза A записывает sha256 одобренного файла в `wave-plan.md` и стартовый промпт волны, а
волна сверяет его с `plan.sha256` своего manifest; это ручная проверка, не гарантия.

## Фаза B — диспетчер

**Поддерживаемый host.** Фаза B в этой версии рассчитана на один стек: Claude Code как
сессия волны и tmux для окон волн и дашборда. На другом host (например, Codex-native
координатор из [profiles.md](profiles.md)) или без tmux режим `--waves` не поддержан:
фаза A сообщает об этом в предполётном чек-листе и фазу B не запускает. Волны там можно
вести вручную — по одной фиче через обычный `/superarmanda`.

Диспетчер ведёт волны по порядку. Для каждой: рабочая копия по [workflow.md](workflow.md) — admitted clone, если host
policy требует admission, иначе обычный изолированный Git worktree → своя
tmux-сессия волны → Claude в режиме auto с протоколом волны и мандатом прогона в системной
инструкции → `/superarmanda --wave <id> --plan <run_dir>/waves.json` (абсолютный путь). Протокол в системной
инструкции переживает `/clear`. Дашборд — отдельная tmux-сессия.

Диспетчер измеряет контекст волны по журналу сессии. На пороге (200k по умолчанию у цепочки 1.4.0+,
300k у цепочки до 1.4.0; `ctx_limit` в `chain.json`) он шлёт `WAB-CHECKPOINT`, ждёт `HANDOFF_READY`, затем делает
`/clear` и `/superarmanda --wave <id> --resume`. Принудительного `/clear` без
`HANDOFF_READY` нет: по таймауту уходит уведомление владельцу. Строки `BLOCKED` и тишину
он переводит владельцу уведомлением с командой `tmux attach`; канал уведомлений —
интеграция host (в текущем прототипе — Telegram). **Правило уведомлений (одно на все случаи).** Все
уведомления владельцу о состоянии волны (старт, окно не готово, `BLOCKED`, тишина, запрос
разрешения, закрытое окно, сдача PR, `DONE` без `next-prompt.md`, отказ запуска следующей волны
диспетчером, конец цепочки и т. д.)
идут через outbox: запись в `state.json` (`outbox` записи волны) до отправки, снятие только
после успешной отправки; при сбое транспорта следующий такт повторяет не чаще раза в 5 минут
(и событие `telegram FAILED` — не чаще), а путь, который заканчивается выходом (`watch`,
неудачный `launch`), перед выходом делает до трёх принудительных попыток; остаток доотправит
следующий `watch`, `launch` или `done`. Переход фазы (или метка «уже уведомлено») и запись
уведомления в outbox сохраняются одним `save_state`, отправка — после него: крах сразу после
сохранения не теряет уведомление, его доотправит следующий `watch` или `done`. Доставка — не
менее одного раза: крах или потерянный ответ транспорта после фактической отправки дают дубль. **Подтверждение снимает устаревшие
уведомления волны, кроме «цепочка завершена»**: когда координатор подтвердил волну —
`launch` следующей волны, перезапуск этой же волны, `wab.py done` — из её outbox уходят все
недоставленные уведомления о прошлом состоянии (сдала PR, следующая не запущена, окно
закрылось, окно не готово, `BLOCKED`, тишина и т. п.), чтобы позже не ушло устаревшее;
«цепочка завершена» остаётся до доставки. **Эпизодное уведомление снимается, когда его эпизод закончился**,
даже без подтверждения: у каждого ключа outbox есть свой конец эпизода (таблица
`NOTICE_EPISODE_ENDS` в `wab.py`; окно вернулось, handoff прошёл `/clear` + сообщение продолжения, новая
сессия привязана, волна записала статус, окно закрылось и т. п.), и недоставленное уведомление
об уже закончившемся эпизоде уходит из outbox тем же сохранением, а не после восстановления
Telegram. Экранные эпизоды (запрос разрешения на экране, тишина, выход из режима auto)
заканчиваются ещё и на экране: таблица `SCREEN_EPISODE_ENDS` применяется в одной точке
(`end_screen_episodes`) в каждом такте с живым окном — до любой ветки такта, которая
возвращается раньше (`BLOCKED`, `/clear` + сообщение продолжения, checkpoint), и до отправки outbox.
Поэтому, если запрос разрешения ушёл с экрана, пока волна стоит в `BLOCKED`, после
восстановления Telegram уходит только «ждёт тебя», а не устаревшее «ждёт подтверждения»
(так же для тишины и выхода из auto). Уведомления других, неподтверждённых волн не
трогаются; переход диспетчера к следующей волне сам по себе подтверждением не считается.
Недоставленное «волна завершена» при `launch` следующей волны тоже снимается — осознанно:
координатор, запустивший её, уже действует по `events.log` и `result.md`.
Голый вызов отправки остаётся только в `wab.py notify` (ручная отправка). Если Telegram
не настроен, повторять нечего.

**Без Telegram сигнал локальный** ([#40](https://github.com/bronxtc52/skill-superarmanda/issues/40)).
Каждое уведомление, которое без транспорта даёт `notify(skipped)`, тут же показывается
`tmux display-message` всем клиентам того tmux-сервера, где живут окна волн (`WAB_TMUX_SOCKET`
или сервер по умолчанию): одна строка отрисованного уведомления (`render_notice()`, см. «Цитата волны»), до 150 символов; сбой tmux такт не
роняет и даёт одно событие `display-message failed` на эпизод. Уведомления, требующие
действия, открывают сигнал в `<run_dir>/ATTENTION`. Информирующие (`INFO_NOTICES`: «стартовала волна»,
«волна завершена», «развилка закрыта по политике», «цепочка завершена») его не открывают
([#55](https://github.com/bronxtc52/skill-superarmanda/issues/55)): диспетчер сам запускает следующую
волну после DONE и подтверждения координатора не будет, так что сигнал «завершена» висел бы вечно.
Недоставленное «волна завершена» по-прежнему ждёт в outbox до подтверждения координатора, а автозапуск
следующей волны диспетчером закрывает ещё открытый сигнал `done` предыдущей (остался, например, от
state старой версии), не трогая её остальные уведомления. Сигнал содержит: время (пояс владельца), волну, первую строку шаблона уведомления (1.2.7), команду
`tmux … attach -t <сессия волны>`. Файл переписывается атомарно последним открытым сигналом
и удаляется, когда эпизод закончился (волна записала не-`BLOCKED` после `BLOCKED`, подтверждение
координатора — `launch` следующей волны, перезапуск, `done`, и любые другие концы из
`NOTICE_EPISODE_ENDS`). Рецепт координатора без Telegram — монитор журнала:
`tail -F <run_dir>/events.log | grep --line-buffered 'BLOCKED\|stopped\|merge gate'`
и/или опрос `wab.py attention <chain>` (код 1 — есть открытый сигнал).

На `DONE` диспетчер проверяет гейт и мерджит PR волны. Следующая волна стартует на
свежем `origin/<base_branch>`, а не на ветке предыдущей волны. `gh pr merge` локальный
ref не обновляет, а при merge queue вообще только ставит PR в очередь. Поэтому
диспетчер сначала ждёт, пока `gh pr view <N> --json state,mergeCommit` покажет
`MERGED`, и берёт `mergeCommit.oid`; потом делает `git fetch origin <base_branch>` и
проверяет, что merge-коммит предыдущей волны — предок полученного SHA
(`git merge-base --is-ancestor`). Не предок — `BLOCKED`, волна не стартует. После последней
волны «Релиз» из плана — итоговый отчёт по цепочке.

**Состояние:** диспетчер (`wab.py`), дашборд (`dash.py`) и гейт мерджа (`gate.py`) реализованы в
`scripts/waves/` (W4, W5); команды — в разделе «Команды» ниже. Мердж задаётся полем `merge_gate`:

- нет поля или `""` — при `DONE` не-последней волны диспетчер передаёт цепочку координатору (`awaiting_merge`,
  команда передачи в журнал, событие «no merge_gate: handing off to coordinator»); сам мерджить и запускать
  следующую волну он не будет. Последняя волна завершает цепочку как раньше;
- `external` — то же, плюс в уведомлении о сдаче строка «Гейт: …» со словесным вердиктом (пройден, пройден с
  незакрытыми тредами, ждёт, не пройден, не проверен); команда, путь скрипта владельца и причины — в `events.log`
  (`hand-off gate: …`), не в уведомлении (передача от этого не зависит);
- `auto` (нужен `repo`) — диспетчер сам прогоняет гейт, мерджит и запускает следующую волну после подтверждённого
  мерджа. Ниже.

### Гейт мерджа: `merge_gate: auto`

По `DONE` окно волны **не закрывается**, фаза `gate`. Не чаще раза в `GATE_POLL_SECONDS` (60) диспетчер собирает
факты — только GitHub API (`gh api`, все страницы, не `statusCheckRollup`) и manifest — и считает вердикт
(`gate.py`, чистые функции, тесты на фикстурах). Волна может забрать `DONE`, пока факты собираются: при `pass` и
`fail` (и при `merge_gate: external` — после сбора вердикта для передачи) диспетчер перечитывает `status` прямо перед
действием — не `DONE` уже (другая строка) → фаза `running`, ничего не делается (ни ready/merge, ни `BLOCKED` поверх нового
статуса, ни передачи с закрытием окна); пусто или не читается → ничего не делается, решение на следующем такте. PR волны ищется по ветке рабочей копии
(`gh pr list --head <ветка> --base <base_branch> --state all --limit 1000`, с повторной фильтрацией по `baseRefName` и по репозиторию-источнику: `--head` совпадает только по имени ветки, поэтому PR из форка с той же веткой отбрасывается — ветка волны пушится в сам `repo` цепочки. Открытый, иначе самый новый; два открытых — сбор фактов падает, а не выбирает по номеру; база или репозиторий-источник неизвестны — тоже не угадывает).


**Какой manifest судит гейт.** Не фиксированный `superarmanda/manifest.json`, а manifest текущего прогона: последняя запись
`<каталог волны>/runs.json` (общая функция `current_manifest` в `wab.py`). Её используют гейт, `owner-merge`, дашборд и
`wab.py status`. Без `runs.json` или при пустом списке прогонов берётся стандартный `superarmanda/manifest.json`, как и раньше.
Отказы закрытые, вердикт `fail` с причиной `manifest: …` и без отката на стандартный путь: `runs.json` нечитаем, не того
формата, слишком большой (больше 2 МБ), не обычный файл (FIFO, симлинк) или чужой волны; в записи нет абсолютного пути; файла нет; путь не обычный файл; физический путь (с учётом
симлинков) лежит вне каталога волны. Выбор прогона никогда не бросает исключение: любая ошибка чтения, разбора (в том числе слишком глубокая вложенность JSON) или проверки записи — закрытый отказ. Причина `manifest: …` идёт первой в `reasons`, остальные причины вердикта (CI, `MERGED_OUTSIDE`) сохраняются.

**Риск волны и два ревью (1.2.2, #86).** Риск волны гейт берёт из одобренного `<run_dir>/waves.json`, запиненного
`plan_sha256` в `chain.json` (`wab.plan_wave_risk`); из manifest — артефакты ревью. План не
читается, не совпадает с пином, не разбирается как план или волны в нём нет — закрытый отказ `fail` с причиной
`план волн: …`, а не «волна не high». Manifest может риск волны только поднять, но не опустить: для manifest
`version: 2` риск волны — наибольший из риска в плане, копии волны `wave.risk` (её кладёт `init --from-plan`) и
`review_policy.level`. Поэтому снятый из `chain.json` идущей цепочки пин или заниженный `level` не делают high-волну
волной ниже high. Копия волны сверяется с `plan.wave_sha256` того же manifest: не совпала — `fail`. Правила:

- **High-волна:** каждая задача manifest, независимо от её собственного `risk`, обязана иметь оба ревью текущего HEAD —
  `cross_provider_reviewer` и `second_reviewer`, один `claude-host` (Astra) и один `codex-host` (Fable) по одному пакету,
  либо засчитанный запасной маршрут `codex-host-opus` с quota evidence того же HEAD и пакета. Проверяют это функции
  `state.py` (`high_risk_gaps`: модель coder и tester не слабее политики ролей manifest для high, проверенные отчёты, пара профилей, один пакет, quota
  evidence), а не их копия. Manifest `version: 1` или `review_policy.level` ниже `high` в high-волне — `fail`; причина
  называет действие: новый прогон волны с `state.py init` на текущей версии скилла (`--from-plan` берёт риск волны).
- **Волна ниже high:** два ревью нужны каждой задаче, чья политика в manifest `version: 2` — `high` (больший из
  `review_policy.level` и `risk` задачи). Manifest `version: 1` судится по правилам 1.2.0; если он несёт записи версии 2
  (`review_policy`, `risk` или `review_history` задачи, `second_reviewer`, поля `model`/`profile` результата), это
  пониженный вручную прогон — `fail` с тем же действием «новый прогон волны».
- **Обязательные роли задачи high (1.2.4, #86; модель — по политике ролей с 1.4.0).** В high-волне у каждой задачи, какой бы `risk` у неё ни стоял, и в любой
  волне у задачи с политикой `high` гейт требует зачёт `internal_reviewer` (запись до первого внешнего пакета задачи
  на его HEAD, дереве и эпохе — кредит = HEAD + дерево + эпоха, ключ `internal_review`) и `final_check` (`pass` на HEAD PR и дереве рабочей копии после последних
  результатов обоих ревью задачи и после закрытия последнего круга исправлений и любой другой записи ролей готовности и `fix-loop` задачи — последнее слово,
  `after_reviews`, `after_fix_cycles`, `after_epoch`). Правило одно — `state.fable_role_gaps`, гейт его вызывает, а не
  копирует; причина называет роль, что с ней не так и действие: какой командой записать (`state.py task-result --role
  final_check …`) либо «новый прогон волны» (внутреннее ревью после первого пакета в этом прогоне уже не засчитать).
  `unavailable`, `error`, `incomplete` и `findings` сверки, сверка на другом HEAD или дереве — `fail`. Версия политики
  в manifest гейт не ослабляет: manifest с `review_policy.version` `1.2.1` (прогон 1.2.1–1.2.3) в high-волне или с
  хоть одной задачей политики `high` — `fail` с действием «новый прогон волны»; в волне ниже high без задач high такой
  manifest судится как раньше.
- **Гейт не верит сохранённому статусу.** Статус `ready_for_pr_review` необходим, но не достаточен: для manifest
  `version: 2` готовность пересчитывается `state.task_ready`. Путь `needs_fix` + `accept_limitation` второе ревью не
  обходит. Гейт читает `review_history`: непокрытые `findings` ревью этого HEAD, ревью Fable на этом HEAD при
  записанном раньше запасном Opus и текущий результат ревью, которого в истории нет (правка manifest руками), — `fail`.
- Ниже high второе ревью необязательно: его `unavailable`, `error` и `incomplete` гейт не блокируют (как и
  `state.py where`), а `findings` требуют `fix-loop`, как у любого ревьюера.
- **Записи политики high у задачи ниже high.** `state.py` ведёт `review_history` и пишет поля проверенного отчёта
  (`profile`, `artifact_sha256`, `review_session_id`, `fallback_for`, `quota_evidence`) только задаче с риском `high`
  и риск никогда не понижает. Если задача manifest `version: 2` несёт их, а её риск в manifest ниже `high` — риск
  задачи или `review_policy.level` понижен вручную: `fail` с действием «новый прогон волны». Сама роль
  `second_reviewer` следом не считается: ниже high это необязательное ревью.
- **Цепочка без `plan_sha256`** (старый `chain.json` или пин убрали) плана не имеет: риск волны берётся только из
  manifest `version: 2` (`wave.risk`, `review_policy.level`), manifest `version: 1` судится по правилам 1.2.0.
  Новая цепочка без пина не стартует (раздел «Ревью плана: `plan-review/`»).
- **Известная граница: manifest не подписан.** Гейт ловит небрежную и частичную правку, но не доказывает
  происхождение записей. Неотличимо в принципе: (1) manifest, вычищенный до безупречного `version: 1` (без
  `review_policy`, `risk`, `review_history`, `second_reviewer` и полей `model`/`profile` результатов), в волне ниже
  high или в цепочке без пина выглядит как живой manifest 1.2.0 — тот тоже несёт `wave.risk: high` при `version: 1`,
  поэтому копия волны правила для `version: 1` не поднимает (в high-волне по запиненному плану такой manifest —
  `fail`); (2) manifest `version: 2`, в котором согласованно исправлены `review_policy.level`, `wave.risk` и
  `plan.wave_sha256` до записи первого ревью, в цепочке без пина; (3) отчёты ревью и quota evidence гейт не
  перечитывает — верит полям, которые `state.py` проверил при записи; (4) manifest `version: 2`, из которого
  согласованно вычищены все следы high — `review_policy.level`, `risk` задач, `review_history`, поля проверенного
  отчёта у результатов, а у manifest из `init --from-plan` ещё и `wave.risk` с `plan.wave_sha256`, — проходит с
  одним ревью в волне ниже high, в том числе под пином: пин поднимает правила только high-волне, а задачу
  с собственным риском `high` в волне ниже high без следов от обычной не отличить. От (1) и (2) защищает пин
  плана в `chain.json`, лежащем вне каталога прогона: не убирай его у идущей цепочки. От (4) пин не защищает:
  надёжнее планировать задачи про безопасность и маскировку high-волной — её правила держит пин, а не manifest.
  `wave.risk` не строкой из `low|medium|high` (список, объект, число) — `fail` с причиной и действием «новый
  прогон волны», а не исключение и вечное ожидание (1.2.3).

Причина отказа называет действие: какого ревью или зачёта нет и какой командой его записать (`state.py task-result
--role second_reviewer`, `--role final_check`), либо «новый прогон волны».

| Вердикт | Когда | Что делает диспетчер |
|---|---|---|
| `wait` | нет check-runs на HEAD; хоть один не `completed`; Codex не завершил ревью на HEAD; HEAD PR ≠ проверяемый; любая ошибка сбора фактов | ждёт, событие один раз на причину; ничего не мерджит |
| `fail` | PR не найден, закрыт без мерджа или уже смержен вне гейта; check-run `completed` с `conclusion` ≠ `success`; P0/P1 Codex на HEAD; manifest нет/битый, `head` ≠ `headRefOid`, нет задач, статус задачи не `ready_for_pr_review` (кроме `needs_fix` при принятом `accept_limitation` ревьюера как последнем решении), результат другого источника (`github_codex_review`, `coderabbit`) не `pass` на HEAD (кроме `coderabbit` `unavailable` — CodeRabbit необязателен, это не блокирует), нет tester `pass` или cross_provider_reviewer без `pass`/решения на этом HEAD (`findings` с `fix-loop --defer` той же роли не раньше результата — наравне с `pass`, и для `github_codex_review`/`coderabbit` тоже); дерево не то (ниже) | статус волны `BLOCKED: merge gate: <причины>`, те же причины в окно волны, фаза `running`, сообщение в окно хранится в записи волны (`gate_fail_msg`) и доставляется как запрос контрольной точки: сбой tmux до вставки или до Enter повторяется следующими тиками и после рестарта `watch`, дважды не шлётся; обычное уведомление BLOCKED (в Telegram только причина). Следующий `DONE` снова идёт в гейт |
| `pass` | всё прочее | см. ниже |

**PR уже смержен вне гейта.** Если владелец смержил PR волны сам, гейт больше никогда не даст `pass`, и строка
`BLOCKED: merge gate: PR уже смержен вне гейта` называет выход готовой командой:
`python3 <wab.py> owner-handover <chain.json> <волна> <run_id>` (сначала остановить `watch`). Команда до любой записи
проверяет: `run_id` и identity прогона; замок прогона (`dispatcher.lock`; занят — отказ «останови watch»); волна —
текущая, не `awaiting_merge`/`done` и не `merging` (там диспетчер сам видит MERGED); PR ветки волны (тот же поиск, что
у гейта) в состоянии `MERGED` с merge-коммитом; `headRefOid` PR равен HEAD рабочей копии волны (смержено ровно то,
что сдала волна); после `git fetch origin <base>` merge-коммит — предок `origin/<base>`. Любой отказ — выход ≠ 0, и
`state.json` не тронут. Успех одним сохранением: фаза `awaiting_merge`, запись `owner_handover` (`pr`, `head`,
`merge_commit`, `at`), `pending_exit` для живого окна (сразу же `/exit`), устаревшие уведомления волны сняты; событие
`<волна>: owner-handover: PR #N смержен владельцем`. Дальше — напечатанная команда: `launch` следующей волны и
`watch`, для последней — `done`.
Ограничение (#37, принято владельцем): `owner-handover` запускать, когда волна в `BLOCKED` (волна стоит). Гонка с
живым окном — худший исход: следующий `launch` откажет, коммиты остаются в ветке волны.

Вердикт `pass` подтверждается вторым сбором фактов: если между чтениями изменилось критичное (check-run перезапущен,
появилось ревью или замечание, треды, draft), вердикт `wait` «факты изменились во время сбора».

`gate.py` в этой версии по-прежнему читает факты PR через REST (`gh api` GET; треды — GraphQL), осознанно: гейт работает в диспетчере, при сбое сбора отвечает `wait` (fail-closed, мерджа нет) и повторяет тик. Перевод гейта на GraphQL — отдельная задача (в `pr_review.py check` уже GraphQL, #20).

Успех проверки — только `status == completed` и `conclusion == success` (`skipped`/`neutral` гейт не пропускает).
**Codex завершил на HEAD** — только по (а) ревью `chatgpt-codex-connector[bot]` (тип Bot) с `commit_id == HEAD` и
состоянием `COMMENTED`/`APPROVED`/`CHANGES_REQUESTED` (`PENDING`, `DISMISSED` — нет) или (б) комментарию этого бота с
маркером `<!-- codex-pull-request-review-summary -->` («Codex Review Summary»): строка его таблицы со статусом
`**Completed**` и коммитом в ячейке ровно `` `<sha7..40>` ``, который API (`repos/R/commits/<sha>`) сводит к HEAD
(строки разбираются по одной; `In progress` и чужие строки не доказательство). 👍 и «clean»-комментарий
(«Didn't find any major issues») **не считаются**: реакцию и текст комментария может поставить или отредактировать кто
угодно, а ревью и сводка привязаны к коммиту самим GitHub. Ревью старого HEAD не считается. Inline-комментарий привязан к HEAD только по `original_commit_id` (GitHub переносит `commit_id` открытого комментария на
последний коммит PR, поэтому по нему старое замечание выглядело бы замечанием HEAD). P0/P1 — такой комментарий бота с бейджем
`![P0 Badge]`/`![P1 Badge]`.

**Привязка к дереву.** Рабочая копия волны чистая (`git status --porcelain` пуст), её `HEAD` == `headRefOid`, и
`tree_fingerprint` каждого засчитанного результата (tester, cross_provider_reviewer) равен `state.py` fingerprint
этой копии: результат, полученный на другом или грязном дереве, не засчитывается. Находки cross_provider_reviewer на HEAD
засчитываются, только если у задачи есть решение владельца `accept_limitation` с `source: cross_provider_reviewer`,
записанное не раньше самого результата (старые решения, другой источник, `invariant`, `cut_surface` не в счёт).
Так же засчитываются `fix-loop --defer` и `fix-loop --accept` ревьюера на этот результат (`state.is_covered`).
Запись manifest с неизвестным ключом (верхнего уровня или задачи) — закрытый отказ гейта
(`unknown record type …`): гейт не судит о том, чего не знает. Pass при принятых medium/high несёт в
`reasons` строки `accepted <sev> <источник>: <note>` и поле `accepted`; диспетчер пишет событие
`<волна>: merge gate passed with accepted limitations: …`, на мердж это не влияет.

**После `DONE`.** Пока волна в `DONE` (фазы `gate`/`merging`) диспетчер помнит HEAD PR, увиденный
при первом сборе фактов (`done_head`). Другой HEAD позже — волна правит PR после `DONE`: ровно одно
событие на каждую смену `<волна>: волна правит после DONE: <старый12>→<новый12>`, запомненный HEAD
обновляется. Память сбрасывается, когда волна сама сняла `DONE` или гейт не пройден (правка по
`BLOCKED: merge gate` законна). Существующее событие «HEAD сменился после гейта» остаётся.

**`pass`.** Диспетчер запоминает проверенный sha (`gate_sha`, `gate_pr` в записи волны), фаза `merging`:

- нет незакрытых тредов ревью и PR draft — выполняется ТОЛЬКО `gh pr ready` (один раз на sha, отметка `ready_called`):
  фаза возвращается в `gate`, `gate_at = now`, мердж не вызывается — перевод в ready может запустить новые проверки
  (`ready_for_review`), и следующий сбор фактов (не раньше `GATE_POLL_SECONDS`) гейтит уже не-draft PR. Если GitHub
  всё ещё показывает draft или ready отклонён — скрипт владельца вместо повторных ready;
- нет незакрытых тредов ревью и PR не draft — ровно один
  `gh pr merge <N> --repo <repo> --squash --match-head-commit <sha>` (отметка о вызове сохраняется **до** него: ни
  перезапуск, ни повторный тик не мерджат тот же sha второй раз). Отказ (в том числе харнесса) — статус `BLOCKED`,
  в Telegram «гейт пройден, но мердж не выполнен» со словесной причиной, а скрипт владельца в `~`-форме и текст отказа — в `events.log` и в `wab.py status` (не сырая `gh pr merge`: скрипт заново гейтит; draft только переводит в ready и выходит (rc 0, «запусти скрипт ещё раз»), на не-draft мерджит с `--match-head-commit`; `owner-merge` принимает фазы `merging` и `awaiting_merge`); волна остаётся в `merging`;
- есть незакрытые треды — **ничего не мерджится**. Диспетчер пишет короткий исполняемый скрипт владельца
  `~/.cache/wab/<волна>.<sha12>.<id16>.merge`, где `id16` — sha256 от identity прогона (путь `chain.json`, `chain`, `run_id`, волна, sha) — имена разных прогонов не совпадают, а точки не дают `redact` спрятать путь с настоящим sha (`chmod 700`; в уведомлениях путь в `~`-форме; повторный гейт на другом sha пишет новый файл, старый скрипт отказывает): `exec python3 <wab.py> owner-merge <chain.json> <волна> <run_id> <gate_sha>`.
  Скрипт привязан к прогону и проверенному sha: `owner-merge` отказывает (rc ≠ 0, до обращения к GitHub), если `run_id` в
  `chain.json` другой, `gate_sha` волны другой или вызов старой формы без `run_id`/`sha`; скрипты разных прогонов не
  перезаписывают друг друга.
  `wab.py owner-merge` **заново** прогоняет гейт (двойной сбор): нужен `pass` на том же `gate_sha` и PR (иначе выход ≠ 0
  с причиной, без действий); затем закрывает текущие незакрытые треды (`resolveReviewThread`; тред закрыт, только если ответ содержит
  `data.resolveReviewThread.thread.isResolved == true`, иначе отказ с id треда до `ready` и мерджа), снимает draft и мерджит
  той же командой с `--match-head-commit`. Работает и после передачи при `merge_gate: external` (фаза `awaiting_merge`: сдача с `pass` сохраняет `gate_sha`/`gate_pr`).
Старые незакрытые P0/P1-треды (написаны не на HEAD) мерджу не мешают, но уведомление после гейта называет их число
отдельно («из прошлых коммитов с P0/P1: K»); будильник приходит до гейта и пишет нейтрально («из них с P0/P1: K»). `owner-merge` до любых вызовов GitHub сверяет сохранённую identity прогона в `state.json` (`check_identity`: смена `repo` и
других неизменяемых полей `chain.json` — отказ); нет сохранённой identity — тоже отказ, пин он не пишет. Запись волны он не меняет: `merging` подхватит `MERGED`. Завершение волны после `MERGED` (или сохранённой фазы `done`)
не зависит от текста `status`: строка `BLOCKED: …` диспетчера не мешает, обрыв между сохранением `done` и запуском
следующей волны добирается следующим `watch`. Статус
  `BLOCKED: merge gate passed; N unresolved review threads; owner runs <путь>`; в Telegram (с 1.2.7) только число тредов и строка «выполни скрипт мерджа»: путь к скрипту — в `events.log` и в `wab.py status`.

**Фаза `merging`** (проверка раз в `GATE_POLL_SECONDS`, переживает перезапуск `watch`): `gh pr view <N> --json
state,mergeCommit,headRefOid`. `MERGED` и `headRefOid == gate_sha` — окно закрывается, волна `done`, дальше запуск
следующей волны от свежего `origin/<base>` (`refresh_workdir`, `verify_previous_merge`) либо конец цепочки у последней.
`MERGED` с другим `headRefOid` (после гейта в PR докинули коммит) или `CLOSED` — статус `BLOCKED`, событие и уведомление,
волна `awaiting_merge`, следующая **не запускается**: решает координатор. `OPEN` с тем же head — ждать; `OPEN`, но `headRefOid` ≠ `gate_sha` (допушили после отказа мерджа или пока висит
скрипт владельца) — волна возвращается в фазу `gate`: `gate_sha`, отметка вызова мерджа и прочее забываются, в статус
снова пишется `DONE`, событие «HEAD сменился после гейта: <old>→<new>, гейт заново»; старый sha уже не мерджится, новый —
только после нового `pass`. Ошибка чтения — событие один раз.

### Хвосты фоновых задач и толчок (#68)

В каждом такте фазы `running` (сессия привязана) диспетчер читает дерево процессов окна одним
`ps -ww -A -o pid=,ppid=,etime=,args=` (`process_table()`; PID Claude — `tmux display-message -p
'#{pane_pid}'`; `pgrep -f` не используется) и делает два дела.

- **Сторож хвостов.** Прямой ребёнок Claude с именем shell (`bash`, `sh`, `zsh`, `dash`, `fish`) —
  хвост, если он запущен до последнего `/clear` (`cleared_at` пишется при успешной доставке
  `/clear`; запас 3 с) или живёт дольше `LOOSE_SHELL_MINUTES` (30), а все его потомки — `sleep`
  (или потомков нет). Одно событие `<волна>: фоновые хвосты в окне волны: pid N (<почему>,
  <возраст>): <команда>` на эпизод (эпизод — набор PID: тот же набор молчит, изменившийся — новое
  событие, пустой — конец эпизода). Без автоубийства и без Telegram: событие и пометка
  «⚠ хвосты: N» рядом с контекстом на дашборде (`bg_tails` в записи волны).
- **Толчок на простое.** Фаза `running`, `status` = `RUNNING`, сессия привязана, `idle_nudge_minutes` > 0,
  нет `pending_enter`/`pending_clear`. Экран не менялся и журналы основной сессии и всех её
  агентов не писались `idle_nudge_minutes`; под Claude нет ни одного дочернего процесса (любой
  shell, даже ждущий цикл, и любая другая команда — живая работа); на экране нет запроса прав,
  меню `/exit` и поле ввода пустое (диалог или меню без рамки ввода и непустое поле — не толчок).
  Тогда в окно уходит одно сообщение «[wab] Толчок: …» на эпизод простоя (дайджест экрана) обычным
  путём доставки (`_deliver`). Под замком ввода, перед набором текста или Enter, условия
  перечитываются: статус в файле, экран (тот же дайджест, что у эпизода), журналы (тишина всё ещё
  ≥ `idle_nudge_minutes`: ожидание замка долгое) и дерево процессов. Недоставленный толчок (текст набран,
  Enter не прошёл) уступает любой другой доставке: `_deliver` сначала очищает поле по экрану и
  печатает чужой текст, только когда очистка подтверждена. Повтор Enter допустим, только если в поле ровно текст толчка; иначе (владелец заменил или
  дописал) толчок забывается без Enter и без очистки поля, одно событие `idle nudge dropped`. Любое неизвестное — **fail-closed**: `ps`
  или `tmux` не ответили, PID не найден в таблице, вывод не разобран — толчка нет, одно событие
  `<волна>: дерево процессов недоступно: <причина>` на эпизод. Волна, ушедшая из `RUNNING`, с уже
  набранным толчком: поле ввода очищается (`_abandon_input`). Уведомление `idle` остаётся как было.

### Лимит Fable в окне волны → Opus (1.4.0, #108)

Волна, чей координатор идёт на Fable (`model` в `chain.json` — `claude-fable-5-1`), и упёршаяся в
лимит подписки, простояла бы часы. На каждом такте `watch` диспетчер читает журнал ТЕКУЩЕЙ сессии
волны: признак — строка ассистента основного потока с `error == "rate_limit"` или
`apiErrorStatus == 429` (пишет сам Claude Code; текст сообщения не читается). Строки субагентов
(sidechain) волну не переключают: у субагентов своя модель роли. Волна на другой модели не
переключается никогда. Модель окна — фактическая: `start_session` пишет её в `state.json` полем
`session_model`, поэтому правка `model` в `chain.json` после старта окна детекцию не сбивает.

Действие: событие `fable limit: <волна> → relaunch on claude-opus-5-5`, у волны в `state.json`
`model_override: "claude-opus-5-5"` и счётчик `fable_switches`, фаза `switching`. Шаги
(`fable_switch` = `{sid, step}`: closing → starting → ready → sending) сохраняются до внешнего
действия: окно закрывается, новая сессия с новым `session_id` стартует с `--model claude-opus-5-5`,
и в неё уходит обычное сообщение продолжения `/superarmanda --wave <id> --resume …` со строкой
«модель переключена на Opus из-за лимита Fable; отметь это в PR». Умерший посередине диспетчер
продолжает с сохранённого шага без второго окна, второй сессии и слепой повторной отправки (не
уверен, что ввод дошёл, — событие `NOT resent`). Цепочка не останавливается; перезапуск НЕ
расходует `restarts`, попытки и `max_runs`. Повторно для той же волны не срабатывает (она уже на
Opus); лимит Opus — обычный путь тишины и `ATTENTION`. `launch` той же волны переносит
`model_override` и `fable_switches`; `wab.py status` и дашборд показывают `модель: … (лимит Fable)`.
`/model` в окно не набирается: он меняет глобальный дефолт владельца.

### Будильник

Волне в фазе `running` со статусом `RUNNING` (при заданном `repo`) диспетчер не чаще раза в `ALARM_POLL_SECONDS` (120)
смотрит открытый PR её ветки. Когда все check-runs HEAD `completed` (их не меньше одного) и Codex завершил ревью на HEAD,
в окно уходит **одно** сообщение на HEAD: номер PR, короткий sha, сколько проверок ok и какие неуспешные, вердикт Codex
(чисто / N замечаний, P0/P1: K), число незакрытых тредов. Новый HEAD — новый будильник. Ошибки `gh` не шлют ничего
(одно событие на эпизод); логику простоя это не меняет. Волне не нужно опрашивать CI самой.

## Режим волны

Файлы волны лежат в `$WAB_DIR`: `status` (`RUNNING | HANDOFF_READY | BLOCKED: … |
DONE`), `handoff.md`, `result.md`, `next-prompt.md`. Manifest и подробные отчёты ролей
храни там же, вне worktree, например `$WAB_DIR/superarmanda/manifest.json` и
`$WAB_DIR/superarmanda/reports/`. В `handoff.md` всегда стоит путь к manifest.

Если `status` не читается (каталог на его месте, нет прав, файл исчез между проверкой и
чтением), `watch` не падает: решает по последнему известному статусу и пишет одно событие
`status unreadable` на эпизод (снова читается — эпизод закончен). Задача волны в промпте должна
содержать хотя бы один видимый символ (буква, цифра, знак, символ); одни пробелы, управляющие и
форматирующие символы, комбинируемые знаки, селекторы вариантов и заполнители (U+3164, U+2800,
U+115F, U+1160, U+FFA0) — пустой промпт, запуск отказывает.

### Старт: `--wave <id> --plan <path>/waves.json`

Модель координатора волны задаёт `model` в `chain.json` (у новой цепочки по умолчанию Opus,
`claude-opus-5-5`); Fable координатору не требуется ни при каком риске (1.4.0, #108). Модели ролей
волны отдаёт `state.py role-model` по политике manifest; `role_models` из `chain.json` приходит в
`init --from-plan` через env `SUPERARMANDA_ROLE_MODELS`. Если волна шла на Fable и упёрлась в её
лимит, диспетчер перезапускает её на Opus (раздел «Лимит Fable в окне волны»); первое сообщение
новой сессии говорит об этом — отметь переключение в PR.

Субагентские роли ([workflow.md](workflow.md), «Субагентские роли»; брифы — [role-briefs.md](role-briefs.md))
в волне применяются на шагах 3–7 по тому же правилу: следователь на задаче-баге, внутреннее ревью
и финальная сверка на задаче high (с 1.2.4 обязательны машинно: без зачёта обеих ролей задача не
готова и гейт мерджа high-волны не пройдёт; внутреннее ревью — до первого внешнего пакета, иначе
новый прогон волны), триаж при находках внешнего ревью. Шаг 1 волны берётся из одобренного плана,
поэтому архитектор работает в фазе A (ТЗ и план high-задачи), а не в волне: его отчёт хранится
файлом `<run_dir>/plan-review/architect.md`, запись `task-result` для роли `architect` в режиме волн не
требуется.

0. **Развилка: manifest волны уже существует** (его путь записан в `$WAB_DIR/handoff.md`,
   обычно `$WAB_DIR/superarmanda/manifest.json`) — это перезапуск или продолжение, а не новый
   старт. Иди в «Продолжение» ниже; `state.py init` не вызывай: он отказывает на существующем
   manifest. Есть только `handoff.md`, а manifest ещё нет (контрольная точка во время сверки
   шага 2, до `init`) — `init` не запрещён: прочитай `handoff.md`, продолжи этот старт с
   записанного места и после сверки одобренного плана выполни первый `state.py init` (шаг 3).
   Диспетчер при перезапуске волны сам начинает первое сообщение с пометки «ПЕРЕЗАПУСК волны …»
   (см. «Перезапуск волны»), но правило действует и без неё.
1. Рабочая копия — как в [workflow.md](workflow.md): если host policy требует admission,
   диспетчер передаёт admitted clone; на unmanaged host — обычный изолированный Git
   worktree.
2. **Сверка до `init`** — плана волны в `<run_dir>/waves.json` с фактическим кодом
   на `origin/<base_branch>` после мерджа предыдущих волн. Расхождение, которое меняет
   приёмку, — развилка владельцу через `status` (ниже), а не молчаливая правка плана или
   приёмки. Manifest до ответа не создаётся. Ответ владельца закрепляется только
   поправкой одобренного плана: поправку в `<run_dir>/waves.json` вносит владелец или
   координатор цепочки с его «ок», и новый хеш одобрения пинится так же, как в фазе A.
   После этого волна начинает старт заново с шага 2. Так решение лежит в плане, а не в
   контексте: после `/clear` без manifest волна просто повторяет сверку.
3. Base — `origin/<base_branch>` после `git fetch` и проверки, что merge-коммит
   предыдущей волны в нём есть (см. фазу B):

   ```bash
   python3 "$SUPERARMANDA_DIR/scripts/state.py" init --manifest <path> \
     --repo <repo> --base <sha> --head <sha> --from-plan <run_dir>/waves.json#<id> \
     ${WAB_PLAN_SHA256:+--expect-sha256 "$WAB_PLAN_SHA256"}
   ```

   `WAB_PLAN_SHA256` ставит диспетчер, когда в `chain.json` задан `plan_sha256`; план
   изменился после «ок» — `init` отказывает и manifest не создаётся. Переменной нет
   (пина нет) — флаг не передают.

   **Счётчик прогонов волны.** `init --from-plan` при заданном `WAB_DIR` (его ставит диспетчер)
   дописывает прогон в `$WAB_DIR/runs.json` (`{version, wave, runs: [{index, manifest, created_at,
   plan_sha256}]}`; файл лежит в каталоге волны вне worktree) и кладёт в manifest `run: {index, max}`.
   Лимит — `--max-runs`, иначе файл `$WAB_DIR/max-runs` (одна строка с целым; диспетчер пишет его при
   запуске волны и обновляет, когда `max_runs` в `chain.json` меняется на лету — так поднятый лимит
   доходит до уже идущей сессии; испорченный файл — закрытый отказ), иначе переменная `WAB_MAX_RUNS`
   (запасной путь, значение на момент старта сессии), иначе 2. Флаги `--max-runs`/`--runs-file` обычно не передают: всё берётся из
   окружения. Сверх лимита `init` отказывает и manifest не создаёт; волна пишет
   `BLOCKED: [class=blocked_cap rec=owner red=no] …`. Повреждённый `runs.json` или `runs.json` другой
   волны — закрытый отказ. Прогон записывается в `runs.json` раньше manifest: если процесс убит между двумя записями, остаётся учтённый, но не созданный прогон — кап не превышается, бюджет лишь уменьшается. Обычный `/superarmanda` без `--from-plan` и без `WAB_DIR` не считается.
   **Какой manifest считается текущим (1.1.1, #76).** Гейт мерджа, `owner-merge`, дашборд и `wab.py status` берут manifest
   последнего прогона: последнюю запись `runs.json` этой волны (путь внутри каталога волны); без `runs.json` или
   при пустом списке — стандартный `superarmanda/manifest.json`. Отказы закрытые (см. «Гейт мерджа»). Manifest и `runs.json`
   пишет только `state.py`: волна и координатор файлы manifest не переставляют и не переименовывают. Второй прогон
   открывается `init --from-plan` на НОВОМ пути (например, `superarmanda/manifest-run2.json`), а первый остаётся на месте.
   `state.py where` отдаёт `run` (`index/max`) и `last_run` (`true` на последнем разрешённом прогоне;
   `max` — ЖИВОЙ лимит из `$WAB_DIR/max-runs`, поэтому смена лимита на лету сразу меняет `last_run`; нет `WAB_DIR`,
   файла или в нём не целое 1..1000 — `where` (только чтение) не падает, а берёт `max` из manifest, #60):
   новых прогонов нет: находки ВНЕ приёмки — `--defer`/`--accept`, нарушения приёмки — обычный круг
   `fix-loop --outcome failed` (в пределах капа 3; кап исчерпан — `BLOCKED class=blocked_cap`).
   `where` отдаёт `accepted` (число АКТИВНЫХ принятий: привязанных к результату текущего HEAD и дерева)
   и `accepted_limitations` (medium/high из них); после `resume` на новый HEAD старые принятия остаются
   в manifest историей, но не показываются.

   В manifest ложатся `plan {path, sha256, wave, wave_sha256, approved_by}` и `wave` —
   копия объекта волны целиком. Дальше источник требований — эта копия; файл плана для
   продолжения не нужен.
4. Шаг 1 не повторяется и `AskUserQuestion` не вызывается: требования, приёмка, риск и
   проверки уже одобрены в фазе A.
5. Шаги 3–7 superarmanda без изменений: красный тест, свежий tester, внешний task review,
   `fix-loop`, PR-гейт.

### Позиция и safe point

На каждой границе шага и круга `fix-loop` записывай позицию:

```bash
python3 "$SUPERARMANDA_DIR/scripts/state.py" mark --manifest <path> \
  --task <task> --step <1..7> --safe-point true|false
```

`mark` отказывает при HEAD или дереве, отличных от manifest: сначала `resume`.
`where` отдаёт `safe_point: true` только для свежей отметки выбранной задачи; после
нового коммита — `false`, для другой задачи — `null`. Отметка ведёт вывод шага только
на шагах 1–3 без результатов ролей. С шага 4 шаг выводится из результатов ролей, а
отметка видна как `marked_step`.

- **Безопасные точки:** между шагами и между кругами `fix-loop`.
- **Небезопасные:** внутри шага 4 (красный тест написан, реализация начата), во время
  ожидания внешнего reviewer, во время Codex-гейта.

На `WAB-CHECKPOINT` доведи **текущий шаг** до safe point. Если есть незакоммиченное —
закоммить WIP локально в ветку волны; push — если его требует host policy (например,
Stop-хук хоста). Затем выполни `resume` под новый HEAD: результаты ролей старого HEAD при этом честно становятся недействительными. Затем
`mark ... --safe-point true`, перепиши `handoff.md` с путём к manifest, запиши
`HANDOFF_READY` и остановись.

**До `HANDOFF_READY` останови фоновые задачи и фоновых агентов** (`TaskStop`) либо перечисли
каждую в `handoff.md`, секция «В полёте», как брошенную: `/clear` их не останавливает, они
остаются дочерними процессами окна. Ожидание процесса — по PID (`while kill -0 <pid>`) или по
точному имени (`pgrep -x`); `pgrep -f`/`pkill -f` по шаблону, который есть в команде самого цикла
ожидания, запрещены: шаблон находит собственную командную строку цикла, ожидание вечное (#68).

### Продолжение: `--wave <id> --resume`

Диспетчер после `/clear` шлёт новой сессии одно сообщение:
`/superarmanda --wave <id> --resume [wab:<цепочка>/<run_id>/<волна>] Каталог волны: <каталог>. …`
(метка стоит в аргументах после `--resume`: по ней диспетчер привязывает новую сессию). То же
сообщение обязано быть единственным источником «куда идти»: позиция — только из manifest.

1. Прочитай `$WAB_DIR/handoff.md`, возьми путь к manifest. Если manifest в нём нет (контрольная
   точка до `init`) — `state.py init` не запрещён: продолжи «Старт» с записанного в `handoff.md` места.
2. `python3 "$SUPERARMANDA_DIR/scripts/state.py" where --manifest <path>` — read-only,
   одна строка JSON: `task`, `task_status`, `step`, `role`, `fix_round`, `verdicts`,
   `open_findings`, `artifacts`, `decision_required_for`, `safe_point`, `marked_step`,
   `tree_matches`, `plan_check`, `next_action`.
3. `tree_matches: false` — сначала `resume` с теми же `--repo --base` и текущим `--head`.
   Результаты старого HEAD недействительны.
4. `plan_check`: `match` — продолжай; `missing` — продолжай по копии волны в manifest;
   `changed` — `BLOCKED: plan changed`, без продолжения.
5. Продолжай с `next_action`. Задача завершена только при `done`; `ready_for_pr_review`
   ещё не конец.

Инвариант: всё, что нужно для продолжения, лежит в manifest и git. Знание, которое есть
только в контексте координатора, — баг. `handoff.md` — путь к manifest плюс свободные
заметки.

### Развилки через `status`

В режиме `--wave` при заданном `WAB_DIR` `AskUserQuestion` не используется: диспетчер
видит только `$WAB_DIR/status`, а вопрос в окне выглядит для него как молчание. Уведомление
владельцу шлёт диспетчер.

Каждая строка `BLOCKED`, которую пишет волна, начинается с машинной метки:
`BLOCKED: [class=<класс> rec=<вариант> red=<yes|no>] <вопрос и варианты>`. Классы —
`needs_decision`, `blocked_cap` (кап 3/3), `plan_mismatch`, `question`; `merge_gate` пишет только
диспетчер. `rec` — рекомендованный вариант коротким токеном (`A`, `invariant`, `cut_surface`,
`accept_limitation`, `new_run`, …). `red=yes`, если ответ касается красной зоны: мердж без
мандата, прод, деньги, удаление, секреты, смена приёмки или скоупа волны. По метке и
`decision_policy` из `chain.json` диспетчер может ответить сам (раздел «Политика решений» выше); правило с
`answer` отвечает фиксированным вариантом — тогда волна действует по варианту из ответа, а не по своей `rec`; строка без метки
или с испорченной меткой обрабатывается как раньше — уведомление владельцу, автоответа нет.

- `needs_decision` (правило двух кругов) — вместо вопроса из шага 6 SKILL.md:
  `BLOCKED: [class=needs_decision rec=<X> red=no] needs_decision <task>: <находка>; варианты:
  invariant | cut_surface | accept_limitation; рекомендую <X>`. Ответ владельца записывается обычным
  `fix-loop --decision ... --note ...`, затем `RUNNING`.
- `blocked` после третьего провального круга: `BLOCKED: [class=blocked_cap rec=new_run red=no]
  blocked <task>: <repro>` (`rec=new_run` — новый прогон в пределах `max_runs`).
- Находки ревьюера только уровня low/P3 (nit, minor) — не `BLOCKED` и не круг fix-loop:
  `fix-loop --defer --source <ревьюер> --note "<что и куда>"`, находки — в остаток
  следующей волны/задачи; кап не тратится, гейт мерджа засчитывает отложенный результат.
- Находка ревьюера medium/high, которая **не нарушает приёмку** («Готово, когда») этой волны, —
  не полируется до бесконечности: `fix-loop --accept --source <ревьюер> --severity <low|medium|high>
  --note "<что и почему принято>"` (те же предусловия, что у `--defer`: результат `findings` на
  текущем HEAD и дереве, задача не `blocked`/`needs_decision`; запись в `acceptances` привязана к
  ровно этому результату; кап не тратится). Принятое ограничение medium/high обязано попасть в
  секцию «Принятые ограничения» тела PR и в остаток `result.md`. Нарушает приёмку — обычный
  `--outcome failed`, не `--accept`.
- Недоступный обязательный reviewer: `BLOCKED` с причиной, а не молчаливый draft.
- Расхождение плана с кодом при сверке до `init`: `BLOCKED: [class=plan_mismatch rec=<X>
  red=<yes|no>] plan mismatch <wave>: <суть>; рекомендую <поправку плана>` (`red=yes`, если
  поправка меняет приёмку или скоуп). Эта развилка всегда идёт владельцу, автоответа на неё нет.
  Ответ закрепляется поправкой одобренного плана
  (см. «Старт»), а не `fix-loop --decision`: manifest ещё нет.

После ответа владельца в окне снова запиши `RUNNING`.

### Отчёты coder и tester

Coder и tester — субагенты координатора, их отчёты копятся в его контексте. В режиме
`--wave` они пишут подробный отчёт в файл рядом с manifest, вне worktree, а координатору
возвращают **не больше 10 строк**: вердикт, путь к отчёту, открытые находки. Путь к
отчёту передаётся в `task-result --artifact`.

### Конец волны

Шаг 7 завершён: PR прошёл Codex-гейт на текущем HEAD по [pr-review.md](pr-review.md),
находки разобраны. Только после этого сними draft отдельным шагом
(`gh pr ready <N>`) и проверь, что `isDraft` стал `false`: draft PR GitHub не мерджит,
а автоматического перехода из draft нет. Если снять draft нельзя — `BLOCKED` с причиной,
а не `DONE`. `result.md` содержит номер PR, `headRefOid`, путь к manifest, выполненные
проверки с итогом и остаток. Последним действием — `DONE` в `status`. Следующую волну
не начинай.

**Треды своего PR (#43).** Если в ветке включено `required_conversation_resolution`, открытый тред
ревью не даёт смерджить даже PR с зелёным гейтом. Закрывать треды волна может только по мандату прогона,
где это разрешено явно (например: «волне — закрывать треды своего PR, которые она разобрала»). Тогда:

- закрываются только треды PR этой волны и только разобранные: находка исправлена коммитом, и в треде
  есть ответ со ссылкой на коммит, или в треде есть ответ с обоснованием, почему находка не исправляется
  (принятое ограничение, отложено в остаток, не находка). Тред без ответа волны не закрывается;
- чужие треды (другие PR, вопросы людей вне владельца и ботов ревью) не закрываются никогда;
- закрытие — GraphQL `resolveReviewThread` после ответа в треде; успех — `isResolved == true` в ответе;
- закрытие идёт до `DONE`, вместе с разбором находок на шаге 7. После `DONE` волна PR не трогает;
- если харнесс или auto mode отказал в закрытии, это не обходится другим путём (REST, скрипт, правка
  настроек ветки): волна пишет `BLOCKED: [class=question rec=owner red=yes] …`, а мердж с открытыми
  тредами идёт скриптом владельца (`owner-merge`), как описано в «Гейт мерджа».

Без такого мандата волна треды не закрывает: она отвечает в них, а закрывает их владелец или скрипт
владельца.

**Мердж делает не волна, даже при мандате:** при `merge_gate: auto` — только диспетчер, после гейта; без поля и при `external` — координатор цепочки или владелец (п.5). Если права host отказывают
в мердже, отказ не обходится. Гейт диспетчера читает manifest и GitHub, а не самоотчёт
волны: `where` по задаче волны показывает `done` на текущем HEAD — то есть есть текущие
`coder`, `tester`, `cross_provider_reviewer` и `github_codex_review` со статусом `pass` — или, у ревьюеров,
`findings`, отложенные `fix-loop --defer` или принятые `fix-loop --accept` ровно на этот результат
(остальные находки проходят через `fix-loop`, отсутствия P0/P1 мало); Codex на текущем
`headRefOid`; PR не draft; все check runs `completed` и `success` (реализация — п.5). Если гейт пройден, а диспетчеру отказали в мердже, владельцу уходит
путь скрипта владельца (`owner-merge`, заново гейтит на том же HEAD); сырая `gh pr merge` человеку не выдаётся: `--match-head-commit` проверяет только sha, а не новые проверки или находки Codex.

## Диспетчер: `scripts/waves/`

Диспетчер ведёт цепочку волн, по одной сессии Claude на волну в tmux (нужен tmux 3.2 или
новее, проверяется до запуска). Только стандартная библиотека; `rich` нужен лишь дашборду и со
skill не ставится: `python3 -m pip install --user rich`. Без него `dash.py` печатает одну строку
«dash.py needs the Python package rich: python3 -m pip install --user rich» в stderr и выходит с
кодом 2 (без traceback); `wab.py` от `rich` не зависит.
Протокол волны, который диспетчер кладёт в системную инструкцию, — `scripts/waves/PROTOCOL.md`.

Команды (`<chain>` — путь к `chain.json`):

- `wab.py launch <chain> <волна> <файл-промпта>` — запустить волну: admission клона,
  `claude --session-id <uuid>`, ожидание готовности окна, отправка задачи.
- `wab.py watch <chain>` — вести цепочку до конца; после падения продолжает с фазы из
  `state.json`, не запуская волну заново и не повторяя уведомления.
- `wab.py status <chain>` — состояние одним экраном.
- `wab.py done <chain> [<волна>]` — завершить цепочку после мерджа PR последней волны (см. ниже).
- `wab.py cleanup <chain>` — закрыть оставшиеся tmux-сессии и панели завершённой цепочки (см. «Закрытие сессий цепочки»).
- `wab.py owner-merge <chain> <волна> <run_id> <sha>` — гейт заново и мердж по запросу владельца (вызывается скриптом `~/.cache/wab/<chain>-<run_id>-<волна>-<sha12>-merge`).
- `wab.py owner-handover <chain> <волна> <run_id>` — владелец сам смержил PR текущей волны (вне гейта)
  и передаёт цепочку дальше; печатает готовую следующую команду (`launch … && watch …` или `done`). См. гейт мерджа.
- `wab.py attention <chain>` — печатает `<run_dir>/ATTENTION` и выходит с кодом 1, пока в нём
  открытый сигнал; файла нет — код 0 (см. «Без Telegram сигнал локальный»).
- `wab.py say <chain> <волна> <файл-текста>` — ответ координатора в окно волны тем же путём, что у
  диспетчера (`send_text`: одна bracketed paste и Enter), с проверкой отправки: после Enter
  `capture-pane`, в строке ввода (`❯ …`) не должно остаться начала текста или свёрнутой вставки и на
  экране — `paste again to expand`; иначе ещё до 3 Enter с паузой, затем ошибка (код 3) с
  причиной. Успех и отказ — строка в `events.log` (первая строка текста после `safe_text()`).
  Текст проверяется как промпт (`read_prompt`). `watch` останавливать не нужно: замок прогона не
  берётся и state не пишется — только ввод в окно и событие. Та же проверка стоит в доставке
  самого диспетчера: текст в превью вставки доставленным не считается, `pending_enter` остаётся, и
  повтор жмёт только Enter с той же проверкой ([#42](https://github.com/bronxtc52/skill-superarmanda/issues/42)).
  `say` отказывает, пока диспетчер должен Enter (`pending_enter`) или ещё не очистил поле
  (`pending_clear`, см. «Очистка поля ввода» в разделе политики), и пишет маркер `owner-answered`
  (формат и смысл — там же), чтобы автоответ не лёг поверх ответа владельца.
- `wab.py notify <chain> <текст>` — собственное сообщение владельца в Telegram: единственный путь, где внешний
  текст не шаблон, потому что его набрал сам владелец в командной строке (`manual_notice()`, текст проходит
  `safe_text()`). Тексты не от владельца этим путём не отправляются.
  **Шаблоны вместо свободного текста (1.2.7, [#83](https://github.com/bronxtc52/skill-superarmanda/issues/83)).**
  Единственная точка выхода наружу — `put_notice → outbox → flush_notices → notify()` (Telegram или
  `display-message`) и `note_attention`/`attention_text` (файл `ATTENTION`). Текст, доходящий до неё, по построению
  продукт шаблона:
  1. `wab.NOTICE_FIELDS` — реестр полей: `chain`, `wave`, `next_wave`, `tmux` (формат имён как в `load_chain`), `event`,
     `pr`, счётчики (`n`, `threads`, `p01`, `attempts`, `runs`, `waves`, `prs`, `restarts`, `questions`), `time` (через
     `hum()`, пояс владельца), `duration`, словарные `cls`, `variant`, `wave_status`, `severity`, `reason`, `red` и
     `question`. Значение, не прошедшее проверку, — «?» (имена, числа, время), для словарных — нейтральная фраза
     («другой вариант», «другой статус», «замечания», «причина записана в журнале событий»), никогда сырое значение.
  2. `wab.NOTICE_TEMPLATES` — одна таблица «ключ → шаблон» на все 23 ключа `NOTICE_EPISODE_ENDS`. Первая строка:
     эмодзи, что случилось, имя цепочки и волна (до 120 знаков); 0–2 строки пояснения простыми словами; для
     вопроса волны — только с флагом (ниже); строка `Время: …` (пояс владельца); у уведомления, требующего человека
     (ключ не в `INFO_NOTICES`), ровно одна строка «Нужно: …» и **последней** строкой `tmux attach -t <сессия>`.
     У информирующих ключей (`started`, `done`, `chain_done`, `policy_answer`) ни действия, ни `attach` нет. Без `class=`/`rec=`/`red=`,
     SHA, путей, имён функций и команд с путями: они — в `events.log`, `wab.py status` и дашборде.
  3. Словари слов: `CLASS_WORDS` (классы вопросов), `ANSWER_WORDS` (`invariant` → «исправить целиком», `new_run` →
     «ещё одна попытка», `accept_limitation` → «принять как есть», …), `STATUS_WORDS`, `SEVERITY_WORDS` (внешний вывод
     важности находки идёт только через `severity_word()`; сырой ключ `dash.finding_counts` наружу не выходит),
     `REASON_WORDS` (причины отказов и действий в окне как закрытые коды).
  4. Одна функция `notice_text(cfg, wave, key, now=None, **fields)` подставляет только поля реестра и поля данного
     шаблона (иначе `ValueError` — ошибка программы); `put_notice(cfg, w, wave, key, value, **fields)` кладёт в outbox
     ключ и поля, а не текст, `notify()` принимает только `Notice`. Время отправки ставится при отправке.
  5. Записи outbox диспетчера 1.2.6 (текст со свободной цитатой, без поля `fields`) при отправке пересобираются по
     шаблону ключа только из полей реестра (цепочка, волна, сессия): свободный текст отбрасывается.
  6. `display-message` — первая строка шаблона и время; префикса `<цепочка>: ` перед эмодзи нет (`sign()` убран).
  7. `ATTENTION`: `signal` — первая строка шаблона по ключу сигнала, `wave` и `attach` — только в формате реестра, иначе
     «?»; вопрос волны в нём нет ни при каком флаге; путь сокета tmux (`-S`) наружу не выходит, имя (`-L`) — выходит.

  **`telegram_quote`** (`chain.json`, `true`/`false`, по умолчанию `false`). С `true` в уведомления, у которых есть
  вопрос волны (`BLOCKED`, «молчит», «окно закрылось», «завершена», «сдала PR», «развилка закрыта», отказы),
  добавляется **первая строка** этого текста через `quote()` (маскировка `safe_text`, как в 1.2.0). Без флага свободный
  текст волны не кладётся даже в outbox. Флаг включают только для репозитория без PII/PHI и данных клиентов; `"true"`, `1`,
  `null` — отказ `load_chain`; `false` равно отсутствию поля; `true` входит в идентичность прогона (смена «нет ↔ true» между
  `launch` и `watch` — отказ `check_identity`), не в `TUNABLE`. Локальные выводы (дашборд, `wab.py status`,
  `chain-result.md`, `events.log`) показывают текст волны через `safe_text` по-прежнему: владельцу он нужен, чтобы ответить.
  **BLOCKED, требующий владельца** (#67): уведомление называет тип вопроса, красную зону и рекомендацию волны словами
  словарей и «Нужно: ответь волне в её окне или текстом командой say»; вопрос волны (первая строка, без `Варианты:`) —
  только с `telegram_quote`. Разбор метки `[class=… rec=… red=…]` и маскировка вопроса — `blocked_fields()`: вопрос целиком
  проходит `safe_text` **до** разбора на вопрос и варианты (разделитель внутри значения секрета, невидимый символ в ключе
  или разделитель строк не выносят значение открытым). Без метки, с испорченной меткой и `BLOCKED: merge gate:` — тип,
  красная зона и рекомендация не называются.
  **Цитата волны** ([#32](https://github.com/bronxtc52/skill-superarmanda/issues/32)). Текст, который
  написала волна или пришёл снаружи, во внешнее уведомление попадает только через `quote()` и только с `telegram_quote`:
  слово с управляющим или невидимым символом (Cc, Cf — нулевой ширины, bidi, мягкий перенос —
  прочие default-ignorable — селекторы вариантов U+FE00–U+FE0F и U+E0100–U+E01EF, CGJ, заполнители хангыля,
  монгольские FVS, в том числе неназначенные, вроде U+2065 и U+E0080 —, Zl/Zp) маскируется целиком, а не чистится (волна не может принести маркеры цитаты `\x02`/`\x03`;
  юникодные пробелы Zs — обычные разделители слов), текст проходит `safe_text(…, owner_paths=False)` — **без**
  исключения «путь скрипта владельца» (п.3 ниже), — длина ограничена `TG_LIMIT`, всё оборачивается в
  маркеры. Эмодзи первой строки — без селектора варианта U+FE0F: `safe_text` маскирует слово с таким символом целиком.
  Единственная точка отрисовки — `render_notice()` (Telegram, display-message, ATTENTION, события):
  слова диспетчера маскируются как раньше (с исключением, путь, который вставил сам диспетчер,
  виден целиком), цитаты — ещё раз и без исключения, и показываются помеченными: блоком
  «Цитата волны:» со строками `> …` либо внутри фразы как «цитата волны: …»; в одну строку (ATTENTION, display-message) сообщение,
  начинающееся с цитаты, сворачивается в «Цитата волны: <первая строка>». Охранные тесты `W3NoticeQuoteGuard` и
  `W7NoticeTemplates` не пропускают `put_notice` с текстом или полем вне реестра.
  **Одна точка маскировки (1.2.0, #81).** Всё, что видит человек, маскирует `wab.safe_text(text, limit,
  owner_paths=False)` и больше ничего: (1) слово (отрезок между пробелами, табами и переводами строк) с невидимым,
  управляющим или default-ignorable символом маскируется целиком до любого разбора и обрезки; одиночный `\r`
  внутри слова — часть слова, и слово, чья склейка без `\r` оказывается секретом, маскируется целиком
  (`password=sec\rret`), между обычными словами `\r` остаётся разделителем строк, `wab.read()` не превращает
  его в `\n`; (2) `redact()` по всему тексту; (3) обрезка до `limit` по безопасной границе: маска `[скрыто]`
  не рвётся (граница внутри неё режет до её начала), обрезки ДО маскировки нет. Строка `events.log`
  маскируется целиком до разбиения на строки (`event()`): разделитель строк внутри секрета не режет его надвое.
  **Маска первой, структурно.** `safe_text` возвращает `wab.Masked` (подкласс `str`: json и state.json берут его как
  строку), а помощники, которые режут или склеивают (`_clip`, `_head`, `_one_line`, `_masked_line`, `dash._clip`), первым
  делом зовут `_require_masked`: текст не `Masked` они сначала маскируют сами (не TypeError: забыть маску нельзя, маска
  идемпотентна). Сырой внешний текст не трогает ни `.split()`, ни срез, ни `" ".join`: `str.split()` режет по
  `\x1c`-`\x1f`, NEL, U+2028/9 и юникодным пробелам, то есть внутри секрета. Тест проверяет это статически (ast): помощники
  зовут `_require_masked`, `Masked(...)` строят только они и `safe_text`, в функциях вывода `split`/`splitlines` идут только по
  замаскированному значению. Юникодные пробелы Zs — разделители слов, как обычный пробел (секрет, разорванный любым
  пробелом, показывает части: ограничение `redact`; закреплено тестом W3Quote).
  Все пути вывода записаны в `wab.OUTPUT_PATHS` (имя, описание); тест идёт по реестру: для каждого пути и каждого
  класса невидимых символов (нулевой ширины, селекторы вариантов, `\r`, default-ignorable) в ключе, значении,
  префиксе токена, длинном hex и base64 ни секрет, ни его часть из 4 символов до вывода не доходит; реестр без
  теста нового пути или тест без записи в реестре — красный тест. Статическая проверка (ast) допускает
  `redact`/`_clean_redact` только внутри `safe_text`. Внешний текст режут только через `safe_text(text, limit)` или после
  неё: любая другая обрезка по длине (срез с верхней границей, `_clip`, `_one_line`, `_head`) в `wab.py`/`dash.py`/`gate.py`
  красная в тесте, пока не внесена в allowlist теста `CUT_ALLOWLIST` с причиной (хеши, уже замаскированный текст, ключи
  дедупликации). Новый путь вывода = строка в реестре и адаптер в тесте
  в одном изменении.
  `redact()` — эвристика, а не гарантия. Правила по порядку:
  1. **По форме и ключу** (везде): PEM-ключи, токены с префиксом (`sk-`, `ghp_`/`github_pat_`,
     `xox?-`, `AKIA`, JWT, токен бота), значение `Cookie`/`Set-Cookie`, `key=value` с «секретным»
     именем, `Authorization`, `bearer`/`basic`, userinfo в URL, e-mail.
  2. **Эвристики**: телефоны; 32+ hex-цифр подряд или группами через дефис (UUID) — **где угодно**,
     в том числе внутри токена (`key-<hex>`, `<hex>-us21`, `id_<hex>`, `v<hex>`, `cache/<hex>`):
     маскируется сама hex-часть; любые 40+ символов base64 без дефиса и с дефисом, если хоть одна
     часть между `-`, `/`, `_`, `+` не похожа на слово (слово — до 3 символов, буквы одного
     регистра или `Capitalized`, только цифры, либо строчные буквы с цифрами до 8 символов).
  3. **Явные исключения** (только они): голый 40–64 hex сразу после метки `commit`/`sha`/`head`/
     `reviewed_head`/`base`/`packet_hash`/`sha256:`; путь URL хоста `github.com` (owner/repo,
     `pull/12/files`, `actions/runs/N`) не трогают телефоны и base64-эвристика, а hex в нём
     маскируется, кроме 40-hex SHA сразу после `/commit/`, `/commits/` или `/tree/`. Query и
     fragment github-URL исключением не являются; правила п.1 действуют и в пути.
     github-URL — это **один URL-токен**: он начинает токен (начало строки, пробел, кавычка,
     скобка, `<`, обратная кавычка, запятая), имеет вид `http(s)://<хост>/…` или голый
     `[www.]github.com/…`, а хост **разобранного URL** равен `github.com` или `www.github.com`
     (не подстрока: `https://example.org/github.com/…`, `?u=github.com/…`, `github.com.evil.example`,
     `https://github.com@evil/…` исключением не являются). Токен кончается на `?`, `#`, пробеле,
     запятой, скобках, кавычках, `<>`: то, что стоит за ним (`…/pull/3,<blob>`, `(…/pull/3)<blob>`),
     маскируется как обычный текст. URL с userinfo (после п.1 — `[скрыто]@…`) исключения не получает.
     Безопасная сторона: в github-пути маскируются `blob/<hex>`, `compare/<sha>...<sha>` и
     `#diff-<hex>` (якорь — fragment); читаемыми остаются только 40-hex после `/commit/`,
     `/commits/`, `/tree/`.

  Известные границы (не маскируется): секрет из одних «словесных» частей (слова через дефис),
  hex короче 32 и base64 короче 40 символов без метки, секрет в пути github.com, не похожий на
  hex и без префикса из п.1, значение с несекретным именем ключа; телефоны других форматов, кроме
  `+…`, российских и 10 цифр группами.
- `wab.py current-tmux <chain>` — имя tmux-сессии текущей волны (его читает `wab-open`).
- `metrics.py <run_dir> [--json]` — замер завершённой или идущей цепочки (#86): по каталогу прогона `runs/<цепочка>/<run_id>` для каждой волны число прогонов (`runs.json` и manifest; файл прогона ищется по `run.index` внутри, без `runs.json` — один прогон по `manifest.json`), фикс-круги (сумма `fix_cycles` задач по manifest волны) и число развилок `blocked_cap` (эпизоды строк `<волна>: BLOCKED: [class=blocked_cap …` в `events.log`, повтор той же записи не считается), итог по цепочке. Только чтение. Нет или не читается файл — «нет данных» с причиной у волны и код выхода 1; нет волн — 2.
- `dash.py <chain>` — дашборд на `rich`, только в терминале (без tty отказывается). Статус
  волны в таблице и на панели текущей волны — одна функция (`wave_status`): файл `status`, а если
  он пуст или не читается — последний известный `last_status`, как решает `watch`. Терминальная
  фаза важнее устаревшего статуса в файле: `dead` — «окно закрыто», `awaiting_merge` — «ждёт
  мерджа», `done` — «готово», даже если в `status` осталось `BLOCKED: …`; так же, если окно
  текущей волны уже исчезло, а `watch` ещё не отметил `dead`. Для такой волны панель не
  показывает команду `tmux attach` (окна нет), а только состояние и последний статус. Испорченный
  счётчик коммитов в state (не целое или отрицательное) и неизвестный (`null`, см. ниже)
  показываются как «?» — и у текущей попытки, и у любой архивной в `attempts`;
  `Ctrl+\` на дашборде открывает текущую волну, внутри окна закрывает. Запускать внутри
  tmux. Схема без реестра: на tmux-сервере одна глобальная привязка `Ctrl+\` (текст — `keys_conf()`,
  в `list-keys` совпадает с привязкой других цепочек), она читает опцию сессии `@wab_open`
  (`<wab-open> <chain.json>`). `dash.py` при старте ставит её на свою панель
  (`set-option -p -t <$TMUX_PANE> @wab_open ...`, на своём сервере из `$TMUX`), при выходе и по
  SIGTERM/SIGHUP снимает (`set-option -p -u`); два дашборда разных цепочек в окнах одной сессии
  не затирают друг друга. Формат `#{@wab_open}` ищет панель, окно, сессию, поэтому цепочки,
  что ещё ставят опцию сессии, совместимы; убитая панель уносит опцию с собой, чистить нечего.
  Привязку `dash.py` ставит, только если её ещё нет или она старой схемы wab; чужую не трогает.
  `wab.py watch` `Ctrl+\` не касается (только снимает устаревшую привязку Shift+Tab старых версий).
  В сессии без опции `Ctrl+\` закрывает popup-клиента или доходит до приложения. `dash.py`
  игнорирует SIGQUIT (иначе `Ctrl+\` в сессии без привязки роняет дашборд). Пути в опции только из
  `[A-Za-z0-9_./+-]` (без пробелов и кавычек), иначе привязка отклоняется событием в журнале.
  Подсказку «`Ctrl+\` — открыть/закрыть волну» панель показывает, только если привязка этого
  дашборда реально включена; при отказе (чужая привязка, недопустимый путь) — «`Ctrl+\` не
  подключён», вне tmux — ничего.
  `wab-open` в popup берёт сервер из `$TMUX` (путь сокета, `-S`), если `WAB_TMUX_SOCKET` пуст.
  Панель «📜 События» показывает `events.log` для человека: `humanize_event` (одна функция) переводит тип события в
  фразу с эмодзи (кто нужен при `BLOCKED`, мердж, контрольная точка, автоответ политики, сбой доставки, толчок, фоновые
  хвосты…), технические детали идут серой второй строкой, неизвестный тип — сырая строка до ~140 символов. Вся строка
  события сначала маскируется `wab.safe_text(owner_paths=False)` (токен с невидимым или управляющим символом — целиком,
  как в уведомлениях), затем оставшиеся C0/C1 нейтрализуются для терминала, и только потом идут разбор и обрезка; имя
  волны распознаётся по `wab.WAVE_NAME`. Подряд идущие одинаковые пульсы (волна, фаза, статус, `restarts`; `ctx` может
  расти) сворачиваются в «без изменений с HH:MM (×N)» (время первого пульса, состояние последнего). Хвост `events.log`
  читается с конца блоками до n+1 свёрнутых элементов (предел 4 МБ), поэтому длинная серия пульсов не вытесняет значимое
  событие. Сам `events.log` не меняется.
  Нечитаемый или пустой (на перезаписи) `status` дашборд показывает последним известным статусом
  волны (`last_status`), как и `watch`, а не `STARTING`.
  Столбец коммитов считает только то, что получил HEAD волны: `launch` сохраняет в записи
  `start_rev` (HEAD рабочей копии после обновления), дашборд считает
  `git rev-list --count <start_rev>..HEAD` в `cwd` волны. Чужие ветки и полученные `fetch`
  remote-refs не учитываются. При переходе в `done`, `awaiting_merge` или `dead` число
  фиксируется в записи (`commits`) вместе с `finished`, так что следующая волна, переключившая
  общий `workdir`, счётчик завершённой не меняет. Если git в этот момент не смог посчитать
  (таймаут, нет git, недоступный `cwd`, ошибка `rev-list`), фиксируется неизвестность —
  `commits: null`, дашборд показывает «?», и последующие сохранения её не пересчитывают: после
  переключения `workdir` следующей волной пересчёт отдал бы завершённой волне чужую историю.
  Если окно мёртвой волны вернулось, оба поля (и `null`) снимаются. Для идущей волны, у которой
  `git rev-list` не отвечает, столбец тоже «?», а не 0. У старых записей без `start_rev` остаётся прежний подсчёт: `git log --all` от
  старта до `finished`. Этот `git log` идёт с таймаутом 10 с: кадр рисуется синхронно, и
  медленный репозиторий, отсутствующий git или недоступный `cwd` дают «?», а не зависший или
  упавший кадр и не ложный 0.
  У перезапущенной волны столбец — сумма текущей попытки и зафиксированных `commits` архивных
  попыток (`attempts`; не-объекты там пропускаются, как в остальных счётчиках). Архивная попытка
  без `commits` (например, `not_ready` или запись старой версии) добавляет 0, с `commits: null`
  (git не смог посчитать при её завершении) делает весь столбец «?»: её
  `start_rev..HEAD` посчитал бы коммиты новой попытки на общем HEAD.

Каталог прогона: `<база>/<chain>/<run_id>`, где база — `run_dir` из `chain.json` или
`<каталог chain.json>/runs`. `chain.json` обязан лежать вне каталога прогона (физические пути, с symlink): иначе волна подменила бы план и пин вместе, `load_chain` отказывает. Журнал волны находится по `session_id`, а после `/clear` — по
метке `[wab:<chain>/<run_id>/<волна>]` в первом сообщении. Служебные строки, которые Claude Code
сам пишет в новый журнал на `/clear` (`isMeta`-предупреждение, эхо `/clear` и его пустой stdout), первым
сообщением не считаются: метка стоит в следующем за ними сообщении продолжения (`/superarmanda --wave <id> --resume <метка> …`). До этого фикса привязка после
`/clear` не срабатывала вовсе, и диспетчер переставал мерить контекст волны (прогон `wave-autobot`, 2026-10-02).

**Сторож замёрзшего контекста** ([#44](https://github.com/bronxtc52/skill-superarmanda/issues/44)).
Если сессия после `/clear` не перепривязана, дашборд часами показывает старый контекст, а настоящий
журнал волны растёт рядом. В записи волны диспетчер хранит `ctx_watch` (привязанный журнал, его размер
и контекст, сколько тактов они стоят, размеры остальных `*.jsonl` того же каталога журналов). Когда
привязанный журнал и контекст не менялись `CTX_FROZEN_TICKS` (5) тактов подряд, а за это время рос
или появился другой журнал верхнего уровня, не принадлежащий другим волнам (их `sessions` и
`attempts`), диспетчер один раз на эпизод пишет событие «контекст не меряется (сессия не
привязана?)» и ставит `ctx_frozen`; дашборд показывает «⚠ не меряется» рядом с контекстом. Только
событие и дашборд, без уведомления. Эпизод кончается, как только изменился привязанный журнал или
контекст: пометка и метка «уже сказано» снимаются, следующая заморозка даст новое событие. Сторож
работает и пока ждёт перепривязки (`await_session`, маркер новой сессии не найден): он смотрит на
последний привязанный журнал и сохранённый контекст; привязка новой сессии кончает эпизод. Журналы
других рабочих копий (другой каталог) не видны.

**Номер PR волны** ([#34](https://github.com/bronxtc52/skill-superarmanda/issues/34)). Колонка PR
дашборда и `chain-result.md` читают `pr` записи волны. Он сохраняется в точке hand-off в любом режиме:
по вердикту гейта (`external`, `auto`) при любом исходе, а без гейта — одним best-effort запросом
`find_pr` (ошибка hand-off не останавливает). Раньше номер ставился только при вердикте `pass`, и
DONE раньше будильника давал «PR: нет».

Поля `chain.json`:

| Поле | Тип | Смысл |
|---|---|---|

| `run_dir` | строка или `null` | база каталога прогона (по умолчанию `runs/` рядом с `chain.json`) |
| `repo` | строка или `null` | `owner/repo`; клон выдаёт `cc-autonomy prepare` |
| `waves`, `titles` | список строк; объект «волна → строка» или `null` | идентификаторы волн по порядку и подписи для дашборда; `titles: null` — то же, что без подписей |
| `tmux_prefix` | строка или `null` | префикс имён tmux-сессий, `[A-Za-z0-9_-]+`; должен быть уникален на tmux-сервере (опция `@wab_open` ставится на реальную сессию дашборда) |
| `base_branch` | строка или `null` | ветка, на свежий `origin/<base_branch>` которой переключается `workdir` перед не-первой волной (по умолчанию и при `null` — ветка из `origin/HEAD`) |

**Admission.** Правила допуска принадлежат host; `wab.py` их не копирует и не проверяет сам
(никаких локальных проверок имени или подписи клона).

- **Сигналы host-политики:** `~/.claude/bin/cc-autonomy.py` (helper) и
  `~/.claude/rules/autonomy-allowlist.md` (правило). Есть хотя бы один (в том числе битый
  симлинк) — host **managed**. Нет ни одного — **unmanaged**.
- **Managed, helper не рабочий** (файла нет, это каталог, битый симлинк, `prepare` вернул
  ненулевой код, не JSON, JSON не-объект (`[]`, `null`, число, строка), `"ok": false` или без
  `admitted_path`) — отказ запуска (fail-closed),
  а не переход в unmanaged.
- **Managed:** первая волна вызывает `python3 ~/.claude/bin/cc-autonomy.py prepare <repo>` и
  сохраняет `admitted_path` в `state.json` сразу (отказ дальше по пути не приводит к новому
  клону на следующей попытке). Следующие волны берут этот же клон без нового `prepare`, и
  `launch` обновляет его так же, как `workdir` (чистое дерево, `fetch`, detach на
  `origin/<base>`, проверка мерджа прошлой волны). Если сохранённого каталога больше нет —
  событие и новый `prepare`.
- **`workdir` на managed host — fail-closed:** принимается, только если после `resolve`
  совпадает с сохранённым в state `admitted_path`; любой другой `workdir`, в том числе до
  первого `prepare` (state ещё пуст), — отказ `SystemExit` «on a managed host workdir comes
  from cc-autonomy prepare». Убери `workdir` из `chain.json`, и клон даст host.
- **Unmanaged:** `workdir` обязателен; без него — ошибка «нет host-политики». `workdir`
  должен быть корнем checkout или worktree: после `resolve` он совпадает с
  `git rev-parse --show-toplevel` (симлинк на корень подходит). Подкаталог чужого checkout —
  отказ «workdir must be the root of an isolated checkout/worktree».

Применённый режим пишется в журнал событий (`admission: …`).

Явный `null` в необязательном строковом поле (`run_dir`, `workdir`, `repo`, `model`,
`base_branch`, `merge_gate`, `tmux_prefix`) — то же, что поле не указано: действует значение по
умолчанию (`tmux_prefix` — `wab-`, `base_branch` — из `origin/HEAD`, `model` — см. ниже).

**Дефолты 1.4.0 (#108).** Цепочка, начатая на 1.4.0+, без `model` идёт на `claude-opus-5-5`, без
`ctx_limit` — на 200 000. Первый `launch` новой цепочки пишет в `state.json` маркер
`"defaults": "1.4"` тем же сохранением, что и намерение запуска. `state.json` с волнами и без
маркера — цепочка, начатая до 1.4.0: её дефолты остаются прежними (`model` — модель CLI по
умолчанию, `ctx_limit` — 300 000), маркер ей не дописывается, а идентичность не меняется (оба поля
tunable), поэтому `watch` и `launch` следующей волны после обновления скилла не отказывают.

Типы проверяются при загрузке до любого использования поля: число, список или объект на месте
строки (и строка с NUL), `true` на месте числа, `""`/`0`/`[]` вместо `telegram` — отказ
`chain.json: <поле> must be …`; `run_dir`/`workdir`, которые нельзя разрешить или создать
(петля симлинков, нет прав, файл на месте каталога), — тоже отказ. При правке на лету `watch`
пишет событие `chain.json not re-read` и оставляет прежние настройки целиком (хорошая правка в
том же сохранении тоже не применяется); любая другая ошибка перечитывания — то же событие, а не
падение `watch`.

**Идентичность прогона.** Все поля `chain.json`, кроме настраиваемых на лету (`ctx_limit`,
`idle_minutes`, `handoff_timeout_minutes`, `tick_seconds`, `telegram`, `titles`, `model`,
`plan_sha256`, `max_auto_answers`, `max_runs`, `idle_nudge_minutes`, `timezone`,
`fable_budget_units`), —
идентичность прогона (`waves`, `repo`, `workdir`, `run_dir`, `tmux_prefix`, `merge_gate`,
`base_branch`, `mandate_sha256` и т. д.; путь к самому `chain.json` в неё не входит). Первый
`launch` сохраняет её в `state.json` (`identity`) тем же сохранением, что и намерение запуска.
Каждый вход координатора — `launch`, `watch`, `done` — сверяет текущий `chain.json` с ней до
любых действий (до `/exit` окнам и до проверок запуска): расхождение — событие «<команда> refused:
chain.json identity differs …» и отказ `SystemExit` с перечнем полей, `state.json` не меняется.
Так ожидающая мерджа волна не авторизует другого преемника, а запуск не идёт против другой
конфигурации, даже если `watch` между вызовами не жил. Старый `state.json` без `identity`
не отказывается: `watch` и `done` дописывают её сразу, `launch` — в сохранении намерения.
Внутри живого `watch` то же поле сверяется на каждом перечитывании (событие `identity changed`,
`watch` останавливается). Новая конфигурация — новый `run_id`.

Числовые поля — положительные конечные числа (не `null`, не строка, не `true`; у
`idle_minutes` допустим и `0`), не больше указанных максимумов: иначе `chain.json`
отклоняется при загрузке, а при правке на лету остаются прежние настройки. Верхняя граница
защищает от `OverflowError` в `time.sleep` и опечаток вроде `1e10`.

Путь установки или chain.json с пробелом или другим символом вне `[A-Za-z0-9_./+-]` отключает `Ctrl+\` (событие в журнале, запасного биндинга нет).

На один прогон работает один диспетчер: `watch` держит `flock` на `<run_dir>/dispatcher.lock`, второй `watch` и CLI-`launch` при занятом замке отказывают. Относительные `run_dir` и `workdir` считаются от каталога `chain.json`. Shift+Tab диспетчер не привязывает; снимает только старую привязку wab (с `wab-open` или `ignore-size`), чужую не трогает.

При `merge_gate: external` после `DONE` волны диспетчер передаёт цепочку координатору: пишет в журнал событий команду и **завершает `watch`** (замок прогона освобождается). Шаги координатора после мерджа PR волны, одной строкой:

```
python3 <абсолютный путь>/wab.py launch <chain.json> <следующая-волна> <run_dir>/<волна>/next-prompt.md && python3 <абсолютный путь>/wab.py watch <chain.json>
```

`<абсолютный путь>` — тот, что диспетчер печатает в журнал событий (команда передачи готова к копированию). `launch` помечает прежнюю волну `done`, запускает следующую, второй `watch` ведёт её дальше.

Если не-последняя волна в `workdir`: перед стартом следующей `launch` требует чистое дерево (`git status --porcelain` пусто), делает `git fetch origin <base_branch>` и `git switch --detach origin/<base_branch>`; PR прошлой волны (её ветка — та, на которой стоит дерево) проверяется через `gh pr view <ветка> --json state,mergeCommit`: нужен `MERGED`, а merge-коммит должен быть предком `origin/<base_branch>` — так проходит и `gh pr merge --squash` (коммиты ветки при squash предками не будут, поэтому по HEAD дерева предок не проверяется). Не `MERGED` или merge-коммита нет в базе — отказ «previous wave not merged». `gh` недоступен или PR неизвестен — событие «merge of previous wave not verified (W5)» и запуск продолжается (при `merge_gate: auto` мердж подтверждён гейтом раньше). `base_branch` берётся из `chain.json`, без него — из `origin/HEAD`, иначе отказ. Первая волна и перезапуск остановившейся волны checkout не трогают.

**Перезапуск волны** (`dead` или `not_ready`, окно закрыто) использует тот же каталог волны: прежняя
запись уходит в `attempts`, а файловые результаты прошлой попытки — `next-prompt.md` и `result.md` —
переносятся в `<run_dir>/<волна>/attempts/<N>/` (N — номер попытки в `attempts`, путь — в её поле
`archive`; занятое имя даёт новый каталог `<N>-<суффикс>`, ничего не перезаписывается). Поэтому
`DONE` новой попытки без своего `next-prompt.md` останавливает цепочку («DONE without
next-prompt.md»), а не передаёт следующей волне устаревший промпт упавшей попытки.

Перезапуск — **продолжение, а не чистый старт**. Сохраняются и не переносятся manifest волны
(`$WAB_DIR/superarmanda/manifest.json` и отчёты ролей рядом), `handoff.md` и коммиты
ветки волны в рабочей копии: это работа упавшей попытки. Архивируются только `next-prompt.md` и
`result.md`. Неизменная копия задачи `<run_dir>/<волна>/prompt.md` остаётся прежней (стартовый
промпт с `--plan`): перезапуск берёт её, а не перечитывает переданный `<prompt-file>`. Если
текст переданного файла отличается от сохранённой копии (BOM и пробелы по краям не в счёт),
`launch` отказывает `SystemExit` до записи `STARTING` в `status` и до сохранения намерения:
manifest, handoff и ветка относятся к старой задаче. Тот же текст (или сам `prompt.md`) —
перезапуск; копии нет (прерванный первый запуск) — переданный файл становится копией, как при
первом запуске. Первое сообщение новой сессии после служебной строки начинается с пометки
«ПЕРЕЗАПУСК волны <волна> (попытка N)»: есть manifest волны — путь «Продолжение»
(`where` → при `tree_matches: false` — `resume` → `next_action`), `state.py init` не вызывать;
есть только `handoff.md`, а manifest ещё нет (контрольная точка до `init`) — прочитать его,
продолжить «Старт» с записанного места и после сверки одобренного плана выполнить первый
`state.py init`; нет ни того, ни другого — «Старт». Пометка добавляется при отправке по полю `restart` записи
волны в state (номер попытки, сохраняется вместе с намерением запуска), поэтому восстановление
после краха на перезапуске шлёт то же сообщение; отправленный текст целиком — в
`<run_dir>/<волна>/first-prompt.md`. Обычный запуск (первая волна, следующая после сдачи) пометки
не несёт.

Закрытие окна завершённой волны — инвариант: **терминальная волна с живым окном несёт `pending_exit`, и любой вход координатора его дожимает**. Флаг сохраняется тем же `save_state`, что и терминальная фаза, и только потом окну уходит `/exit`; это делают все терминальные пути: `DONE` → `awaiting_merge` (сдача координатору), `DONE` → `done` (и последней волны с «цепочка завершена», и перед запуском следующей диспетчером), `DONE` без пригодного `next-prompt.md` → `done` + остановка (при любом `merge_gate`). Дожимают флаг (`close_pending_windows`: `/exit` живому окну, снятие флага, когда окна нет) все входы координатора: старт `watch` (`resume`) и каждый тик, `launch` (сразу после чтения state, ещё до проверок — и отказанный запуск дожимает), `done` (и повторный). `done` после `/exit` ждёт окно до 30 секунд: ушло — флаг снят; не ушло — событие «still open», флаг остаётся, повторный `done` дожимает снова. В этом случае `wab.py done` завершается кодом 3 с сообщением в stderr (цепочка завершена, но окно ещё открыто); повторный `done`, при котором окно закрылось, возвращает 0. Так же ведёт себя `watch`, который сам завершил цепочку (`DONE` последней волны без `merge_gate: external`) или запущен уже после её завершения: после `/exit` он ждёт окно последней волны до 30 секунд; ушло — флаг снят, `watch` завершается кодом 0; не ушло — событие «still open» с командой `wab.py done …`, флаг остаётся, `watch` завершается кодом 3, и координатор дожимает окно повторным `done`. Исключения осознанные: `dead` — окна уже нет; `not_ready` — окно Claude не стало готовым, и его оставляют владельцу посмотреть (уведомление с `tmux attach`), `/exit` туда не шлётся, перезапуск той же волны отказывает, пока окно живо. Если диспетчер упал между сохранением и `/exit`, следующий вход дожимает `/exit` по флагу. Перед обновлением `workdir` и стартом следующей волны `launch` проверяет, что tmux-сессия предыдущей волны (по её имени, на том же сокете) завершена: при `pending_exit` повторяет `/exit` (если этот же вызов ещё не слал) и ждёт до 30 секунд, иначе — отказ `SystemExit` «previous wave session <имя> is still running; wait or close it» до любого изменения state и checkout. На `/exit` сессии с фоновыми задачами (shell, агенты) Claude Code отвечает меню «❯ 1. Exit and stop tasks / 2. Move to background and exit / 3. Stay»: `close_window` узнаёт его и подтверждает Enter, только пока выделен пункт 1 (иначе — событие, без нажатия); ожидание окна подтверждает меню, появившееся после `/exit`. Запуск самим диспетчером (в такте `watch`) после подтверждённого `DONE`: окно волны в фазе `done`, не ушедшее за 30 секунд, закрывается `tmux kill-session` (событие «closed with kill-session (the wave is done)»), и следующая волна стартует — работа такой волны уже смержена, окно держат только остатки (застрявшее меню, фоновые shell). Живая остановка: `mh-creators-mvp` run01, 2026-10-03 — цепочка простояла 9 ч. Если так отказан запуск следующей волны самим диспетчером (в такте `watch`), `watch` не падает: цепочка останавливается с причиной (`stopped` «<волна>: launch of <следующая> refused»), одно событие и одно уведомление на причину (ключ `launch_refused`, снимается только подтверждением координатора), `watch` завершается кодом 3. Сам он запуск не повторяет каждый такт: координатор устраняет причину (закрывает окно) и делает `launch` следующей волны, либо запускает `watch` снова — тот повторит запуск из завершённой волны.

**Последняя волна.** После `DONE` последней волны запускать нечего: после мерджа её PR координатор завершает цепочку командой `python3 <абсолютный путь>/wab.py done <chain.json> [<волна>]` (волна по умолчанию текущая; допустима только последняя и только из `awaiting_merge`; повтор безопасен). Волна становится `done`, `current` — пустым, в журнал пишется `chain finished`. Для не-последней волны `done` отказывает: там после мерджа идёт `launch`.

Уведомления «волна сдала PR, жду мерджа» и «цепочка завершена» подчиняются общему правилу уведомлений (см. выше: outbox, «не менее одного раза», подтверждение снимает устаревшее, кроме «цепочка завершена»). Id волн в `waves` уникальны без учёта регистра (из них строятся имена tmux).

`wab.py launch` отказывает (до подготовки клона, записи намерения и создания окна), если файл задачи не найден, битый симлинк, петля симлинков (`cannot resolve`), не обычный файл (каталог), не читается, не в UTF-8 или пуст: нет ни одного видимого символа (пробелы, BOM, zero-width, управляющие вроде NUL, комбинирующие знаки, селекторы вариантов и заполнители U+3164, U+2800, U+115F, U+1160, U+FFA0, U+FFFC, U+FFFD, U+1D159 не считаются). Проверенный текст (без BOM) читается до переключения `workdir` и сохраняется неизменной копией `<run_dir>/<волна>/prompt.md` после последней проверки и до записи намерения; в state `prompt_file` указывает на копию (исходный путь — `prompt_source`). Отправка задачи и восстановление после краха читают только копию, поэтому файл задачи в рабочей ветке прошлой волны может измениться или исчезнуть при `git switch`. Восстановление, которое только дожимает Enter после краха, завершает старт как обычный путь: метка, уведомление «стартовала» (один раз) и событие `launched in tmux`. `wab.py launch` и `watch` завершаются кодом 3, если волна не стартовала (окно не готово), цепочка остановилась из-за закрытого окна, `watch` завершил цепочку, но окно последней волны не закрылось после `/exit` (дожим — `wab.py done`) или не-последняя волна записала `DONE` без пригодного `next-prompt.md`: файла нет, либо его отклоняет та же проверка, что и `launch` (`read_prompt`: пустой, не UTF-8, не обычный файл и т. д.; причина — в событии и уведомлении). Это действует и при `external`: проверка до передачи координатору, `awaiting_merge` не ставится; одно событие и одно уведомление; `launch` следующей волны снимает остановку. Все цели tmux точные (`=<имя>`), `wv-w1` не заденет `wv-w10`; для приватного сервера есть переменная `WAB_TMUX_SOCKET`: значение со `/` — путь сокета (`tmux -S`), иначе имя (`-L`), пустое — сервер по умолчанию.  Если она пуста, `wab-open` берёт сервер из `$TMUX`. Непустой `telegram` обязан содержать строки `keyvault`, `token_secret`, `chat_secret`, иначе загрузка отклоняется (на живой правке остаются прежние настройки).

### Закрытие сессий цепочки (#57)

Завершённая цепочка не оставляет окон. **Владение**: `start_session` сразу после `new-session` ставит на сессию волны и на её
первую панель опции tmux `@wab_run` = `<цепочка>/<run_id>` и `@wab_run_dir` = абсолютный каталог прогона; дашборд (`register_dash`)
ставит обе вместе с `@wab_open` на свою панель (если панели нет — на сессию), `unregister_dash` снимает все три. «Наше» —
две опции, выставленные именно на этой панели или сессии (читаются `show-options -p -v` / `show-options -v` без
наследования): `@wab_run` равна метке прогона И `@wab_run_dir` (нормализованный путь) равна каталогу этого прогона — два `chain.json`
могут повторить пару цепочка/`run_id` и имя сессии, различает их каталог; совпал тег, а каталог другой или не задан — «не наше»; имя сессии для этого не годится: префикс `tmux_prefix` может совпасть у разных прогонов.

**Когда закрываем.** Признак завершения — `chain-result.md` в каталоге прогона. `watch` закрывает после «chain finished»
и доставки уведомлений; `wab.py done` — после своей обычной логики (смена фазы, уведомления, ожидание `/exit`): если окно
последней волны закрыто этим вызовом, `done` возвращает 0, иначе поведение прежнее (окно живо — код 3). Закрываются сессии
волн этого прогона (имена из `state.json`, включая попытки, с префиксом `tmux_prefix`) и панели дашборда с `@wab_run` этого
прогона и `@wab_open`, указывающим на этот `chain.json`. Опции читаются непосредственно перед `kill-pane`; сессия как таковая не убивается (`kill-session` не вызывается): закрываются её наши панели, и tmux закрывает сессию вместе с последней. В итог попадает только подтверждённо закрытое (код 0 и панели нет в успешном списке); отказ `kill-pane` — событие. Сессия считается ушедшей только при подтверждённом отсутствии (`can't find session`, `no server running`, нет сокета); иной сбой `has-session` — событие «could not confirm what was closed (has-session failed)», сессия и её панели в итог не попадают. `/exit` завершённой волны (`close_window`, ожидание в `done`/`launch`) адресуется только по id нашей панели, найденной в сессии через ту же проверку «наше» и перечитанной перед отправкой, и никогда в активную панель сессии `=<имя>:`; если в сессии с нашей меткой нашей панели нет, окно волны считается закрытым (`pending_exit` снимается, `done` возвращает 0), сессия с чужой меткой — `/exit` не получает, намерение снимается с событием; сессия вовсе без `@wab_run` (запущена wab ≤ 1.0.2) ведёт себя как раньше. Метки читаются списком опций уровня (`show-options -t …`): «опции нет» подтверждается успешным списком, сбой чтения — статус «unknown», при котором не делается ничего (ни ввода, ни `kill`, намерение остаётся до следующего такта). `start_session` берёт id панели из `new-session -P -F '#{pane_id}'` и метит её по id, а не «активную панель сессии». Восстановление после падения между `new-session` и метками (`recover_launch`) метит найденную живую сессию только если она подтверждённо не помечена, её окружение (`show-environment`: `WAB_DIR` = каталог волны, `WAB_WAVE` = id волны, как их передал `start_session`) совпадает и в ней ровно одна панель, подтверждённо без меток (метятся сессия и эта панель по id); иначе — событие «not marked», `cleanup` потом лишь предупредит. Предупреждение `launch` различает прогоны по паре (метка, каталог). Сессия без `@wab_run`
(запущена старой версией) — только предупреждение; с чужим значением (имя переиспользовано другим прогоном) — не трогается;
в нашей сессии есть чужие панели — убираются только наши панели, сессия остаётся. Итог — одно событие
`chain sessions closed: sessions […], panes […]`; повторный вызов ничего не пишет. Ошибка tmux — событие, `watch` и `done` не падают.

**Предупреждение при `launch`.** Запуск первой волны (не перезапуск) ищет на сервере tmux чужие метки `@wab_run` с каталогом
прогона, где есть `chain-result.md` и нет живого диспетчера (`dispatcher.lock` не берётся под `flock`; файл открывается только
на чтение). Для каждой такой цепочки — событие и строка в stderr с командой `wab.py cleanup <chain.json>`. Живые и незавершённые
цепочки не упоминаются, ничего не закрывается; сбой чтения тихий.

**`wab.py cleanup <chain.json>`.** Берёт замок прогона (`dispatcher of this chain is alive` — отказ, код ≠ 0, пока диспетчер жив),
сверяет identity, отказывает без `chain-result.md` (`chain not finished`), иначе закрывает то же, что конец цепочки, и печатает итог.
Повтор — код 0, ничего не закрыто. Нужен для цепочек, завершённых до 1.0.3, и когда закрытие при завершении не удалось.

### Тесты и ручная проверка: только приватный tmux

`tests/helpers/superarmanda_waves_test.py` сам изолируется до первого теста: `TMUX_TMPDIR` — свежий временный каталог, `TMUX`/`TMUX_PANE`/`WAB_TMUX_SOCKET` сброшены, вызов `tmux` без `-L`/`-S` через `subprocess`/`os.system` падает с `AssertionError`, а шим `tmux` в `PATH` отказывает тому же вызову из скриптов (`wab-open`). Ручные проверки — по тем же правилам: `export TMUX_TMPDIR=$(mktemp -d)`, `unset TMUX TMUX_PANE WAB_TMUX_SOCKET`, у каждого `tmux` есть `-L`/`-S`; `dash.py` и `wab.py` на сервере по умолчанию не запускать (иначе глобальный `Ctrl+\` перепривязывается на тестовую сессию).

**Офлайн-сквозной тест цепочки** — `tests/superarmanda-waves-e2e.test.sh` (`tests/helpers/superarmanda_waves_e2e_test.py`, около 25 с, входит в `scripts/run-tests.sh` и CI). Двухволновая цепочка идёт через настоящий код диспетчера (`wab.py launch` → `watch` → `done`, `gate.py`, `state.py`) на подставных `tmux`, `gh` и `claude`: в `PATH` теста только каталог подставных бинарей и `python3`/`git`/`sh`/`env`/`cat`, `HOME` временный, переменных `WAB_*`/`TMUX*` хоста нет, `urlopen` и `socket.connect` бросают исключение, Telegram выключен, время виртуальное. Подставной `tmux` — с состоянием; каждый его вызов обязан нести `-S`/`-L`, экраны вырезаны из живых снимков `tests/fixtures/screens`. Подставной `gh` работает над настоящим локальным bare-«origin»: `gh pr merge --squash --match-head-commit` реально сливает ветку, следующая волна берёт свежую базу. Сессии волн играет тест (между тиками, по тому, что диспетчер набрал в окно; журналы сессий — по формам из `tests/fixtures/transcripts`). Сценарий: W1 пишет `BLOCKED: [class=… rec=… red=no]` → ответ по `decision_policy` → DONE → гейт ждёт CI, падает на красном CI (причина доходит в окно), ждёт Codex, пропускает → мердж → W2 стартует на базе с merge-коммитом W1 → рост контекста → `WAB-CHECKPOINT` → `handoff.md` + `HANDOFF_READY` → `/clear` → новый журнал → `/superarmanda --wave W2 --resume [wab:…]`, привязка сессии по метке → DONE → гейт → мердж → `chain-result.md`. В тот же набор входят мутации: сценарий с отключённым гейтом (красный CI; Codex на старом коммите), без привязки сессии после `/clear`, со «старой» рабочей копией следующей волны, без измерения контекста и без политики решений — оракул обязан провалиться, а цепочка встать. Запуск: `bash tests/superarmanda-waves-e2e.test.sh` (одним файлом — `python3 tests/helpers/superarmanda_waves_e2e_test.py Mutations`).
