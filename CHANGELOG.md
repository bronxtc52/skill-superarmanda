### Исправлено

- `metrics.py` (#113 W4): каждый файл, из которого берётся число, проходит одну проверку идентичности до счёта
  (`_read_checked` → `_runs_of` / `_manifest_checked`). Manifest засчитывается, только если `version` — целое 1 или 2
  (не `bool`, не `1.0`, не строка; как `state.check_schema`) и его `wave.id`, если ключ есть, равен имени каталога
  волны; manifest другой волны — «нет данных». Два `superarmanda/manifest*.json` с одним `run.index` — отказ, а не
  первый файл по имени. Битый симлинк `runs.json` или manifest — файл есть, но не читается (а не «нет файла»), и
  запасной путь через `manifest.json` при нём не срабатывает. Тест `MetricsScript`
  `test_every_counted_file_passes_one_identity_check`; фикстура `tests/fixtures/waves/metrics-run/` получила
  `version` и `wave.id` в manifest.
- `metrics.py` (#113 W4, ревью): каждый читаемый файл (`runs.json`, все `manifest*.json` поиска по `run.index`, `events.log`) открывается одним путём с `O_NOFOLLOW|O_NONBLOCK`, только обычный файл и чтение из проверенного дескриптора — FIFO не вешает замер; чужая волна при поиске по номеру — причина про волну, а не «дубль»; два симлинка на один файл — не дубль (тест `test_every_read_file_is_read_from_one_checked_descriptor`); путь разрешается один раз и открывается именно результат, открытый дескриптор обязан быть ровно разрешённым путём, а не любым файлом волны (Linux — путь `/proc/self/fd` равен ему, пометка ` (deleted)` срезается только в конце; без /proc — `st_dev`/`st_ino`, промежуточные каталоги не защищены; тесты `test_an_intermediate_directory_swapped_inside_the_wave_is_refused`, `test_deleted_suffix_is_cut_only_at_the_end_of_the_opened_path`), любой `OSError` (нет доступа, битый симлинк) — причина, а не traceback, файл больше 16 МиБ (events.log — 64 МиБ) — отказ (тесты `test_unreadable_or_oversized_file_is_no_data_not_traceback`, `test_path_is_resolved_once_and_the_opened_file_is_checked`).
- `wab.py`, `metrics.py`, `dash.py` (#113 W4): служебные строки ответа владельца («marker not written», «status
  rewritten») пишутся отдельным видом события `<волна>: say-note: …` (одна функция `say_note`); `say: ` — только текст,
  ушедший в окно. `metrics.py` узнаёт старые служебные `say:` только в журналах прошлых версий, дашборд показывает
  `say-note` как «отметка ответа владельца не сработала», а не как сообщение в окно.
- `dash.py` (#113 W4): отметка «смена идентичности прогона сообщена» (`_IDENTITY_TOLD`) ставится только после
  успешной записи в `events.log`; упавшая запись повторяется на следующем кадре.
- `state.py` (#113 W4): причина `NEW_RUN` называет свидетеля внешнего ревью один раз и короче —
  `<роль>, witness: <поле manifest>`, без вложенных скобок.

  60 выводятся как `1ч30м`; испорченные `n`/`minutes` записи outbox (строка, `bool`, `None`, `nan`, отрицательное) —

  `test_attention_keeps_the_minutes_the_delivered_notice_showed`).
- `metrics.py` (#113 W4, ревью): один физический файл (`st_dev`, `st_ino` открытого дескриптора) — один прогон во
  всём каталоге прогона: тот же путь дважды в `runs.json`, другая запись пути, симлинк, hardlink, волна-симлинк на
  другую волну — «нет данных», код 1, а не удвоенные фикс-круги (с `run` и без; тесты
  `test_one_physical_file_is_never_two_runs`, `test_one_physical_file_is_never_runs_of_two_waves`). Граница чтения

- `metrics.py` (#113 W4, ревью): испорченный ввод не пропускается молча и не засчитывается. Волна с дублем
  физического manifest — «нет данных» и в столбце «прогонов», как волна-симлинк наружу: один файл не даёт двух прогонов
  ни в волне, ни в итоге (прогон из `runs.json` с потерянным manifest по-прежнему считается). Без `runs.json`
  засчитывается только `manifest.json`, а другой физический файл волны, валидно называющий себя прогоном

  `runs.json`; с `runs.json` — отказ, если `run.index` файла в нём нет (state.py пишет `runs.json` до manifest).
  Висячий симлинк `W*` (внутрь и наружу), петля и `W*`-файл остаются в таблице строкой «нет данных», код 1, а не
  исчезают. Корень волны разрешается один раз: подмена симлинка `W*` после проверки границы не уводит чтение в
  чужую цепочку (тесты `test_without_runs_json_a_second_run_manifest_is_refused`,
  `test_a_run_manifest_missing_from_runs_json_is_refused`, `test_a_wave_entry_that_is_not_a_readable_dir_is_named_not_dropped`,

- Тесты с настоящим tmux (`ExactTargets`, `KeysAndRegistry`, `ChainCleanup`) поднимают сервер одним помощником
  `start_tmux_server`: свежий сокет, сессия-хранитель (сервер не выходит, когда тест закрывает последнюю сессию —
  иначе `has-session` сразу после закрытия ловит выход сервера, «server exited unexpectedly», и закрытие не
  подтверждается), ожидание готовности, остановка с ожиданием. Ожидание — по условию (`wait_for`), а не

- `scripts/run-tests.sh`: наборы идут параллельно, по числу CPU (`RUN_TESTS_JOBS` переопределяет, `1` — прежний

  печатается целым блоком в исходном порядке. Совместим с bash 3.2. Порядок наборов — байтовый на любой машине (glob

## 1.5.3 — 2026-10-12

Цепочка `waves-tails2`, волна W3: отметки автоответов и уведомление `BLOCKED`
([#113](https://github.com/bronxtc52/skill-superarmanda/issues/113), раздел W3; остаток
[#100](https://github.com/bronxtc52/skill-superarmanda/issues/100)). Один инвариант I-W3 на всю поверхность
(комментарий в `wab.py` перед `_fork_keys`) и одна таблица-перебор `W3PolicyMarksAndNotices`.

### Исправлено

- `wab.py` (#113 W3, A1): `policy_key_pending` проверяется по полной схеме — `status` и `text` только eid
  (`EID.fullmatch`), ключ в полёте текущей записи — своей волны и своего `run_id`, архивный (`attempts`) — своей
  волны. `_fork_keys` получает волну и `run_id`. Испорченный или чужой ключ — отказ «отметки автоответов в state.json
  испорчены» владельцу, а не автоответ.
- `wab.py` (#113 W3, A1/A2): миграция `upgrade_record` больше не «отмывает» испорченные отметки: `policy_refusal.status`
  и `policy_key_pending.status` становятся eid, только если это строка `BLOCKED` с валидной меткой (её разбирает
  `parse_blocked_label`, форма 1.4.x), `policy_key_pending.text` — только если это текст фиксированного ответа.
  «garbage», `sha256:abc` и `BLOCKED: [junk] x` остаются как есть и читаются как испорченная отметка.
- `wab.py` (#100 п.15, A3): такт на пустом или нечитаемом `status` сразу после автоответа больше не открывает новый
  эпизод и не шлёт ложное уведомление `BLOCKED` на потолке: эпизод новый, только если штамп другой и файл читается
  как та же строка.
- `wab.py` (#113 W3, A4): уведомление `BLOCKED` после неудачной доставки ответа (и на любом пути без автоответа)
  перечитывает `status`: непустая другая строка его глушит, пустая или нечитаемая — нет.
- `wab.py` (#100 п.11): новый эпизод той же строки после автоответа при испорченной `policy_refusal` и при правиле,
  которого больше нет в `chain.json` (политика изменилась между эпизодами), даёт владельцу одно уведомление вместо
  молчания. То же без предшествующего автоответа (прошлый эпизод отказан на потолке): новый эпизод узнаётся по
  отметке эпизода и свежему непустому чтению `status`.
- `wab.py` (#113 W3, круг 4, A1): учёт эпизода — одна точка `_episode_step` для пути правила и для выхода без
  автоответа. При испорченной `policy_refusal` и ещё не созданной `policy_episode` отметка эпизода создаётся на этом
  выходе (только для строки, к которой подходит правило; строка без правила дедуплицируется по тексту, как в 1.2.0),
  и следующий эпизод той же строки — с `RUNNING` между ними или без — уведомляет владельца ровно один раз, а не
  молчит. Эпизод решается по одному стабильному чтению `status` (штамп → текст → штамп): перезапись между штампом и
  чтением — один новый эпизод, а не два. Пустое или нечитаемое чтение отметку не пишет; испорченная `policy_episode`
  не перезаписывается. Ограничение: одновременная порча `policy_refusal` и `policy_episode` — повторы той же строки
  молчат (waves.md, I-W3).
- `wab.py` (#113 W3, круг 4, F2): миграция `policy_key_pending.text` берёт только полный текст фиксированного ответа
  в замороженной форме 1.4.x (`_LEGACY_FIXED_TEXT`: заголовок с вариантом из закрытого словаря, формулировка,
  `Затем запиши RUNNING в status.`), а не любую строку с префиксом `[wab] РЕШЕНИЕ ПО ПОЛИТИКЕ` — мусор после префикса и
  ответ правила без `answer` остаются как есть и читаются испорченной отметкой.
- `wab.py` (#100 п.17): окно погибло во время доставки до вставки текста — ключ в полёте и `policy_pending` снимаются
  до проброса `_WindowGone`; после перезапуска волны развилка больше не читается как «уже получила автоответ».
- `wab.py` (#113 W3, A5): путь скрипта владельца `~/.cache/wab/<волна>.<sha12>.<id16>.merge` больше не превращается
  в `[скрыто]` в `events.log`, `questions[]` и `chain-result.md`, когда `id16` похож на номер телефона: события передачи
  владельцу и запись вопроса маскируются с `owner_paths=True` (исключение — только для имени, которое диспетчер сам
  вывел для волны и sha этого прогона, и только при существующем файле; остальные маски строки сохраняются). Это
  корень флейка
  `MergeGate.test_an_interrupted_merge_is_handed_to_the_owner_once`.
  Класс закрыт целиком: каждое событие с путём скрипта владельца (результат мерджа неизвестен, отказ мерджа,
  напоминание, открытые треды, гейт передачи при `merge_gate: external`) пишет одна функция `owner_event`, путь цел и
  в `wab.py status`; статическая проверка находит `event()`, собранный из пути скрипта, в обход неё.
  Дашборд показывает путь по общей политике #81 (`owner_paths=False`): там он может быть `[скрыто]` или обрезан —
  команду владельцу брать из `events.log` или `wab.py status`.
- `wab.py` (#113 W3, Codex P2): существование файла `~/.cache/wab/<имя этой формы>` больше не снимает маскировку само
  по себе — волна работает от того же пользователя и могла создать такой файл и написать путь в `status` или вопрос.
  Исключение берёт только имя, которое диспетчер вывел сам (`_owner_script`: волна и sha этого прогона); `wab.py status`
  и `chain-result.md` в новом процессе выводят имена заново из `state.json` (`gate_sha`, `merge_called`,
  `owner_remind`). Поддельный путь волны маскируется, путь диспетчера цел.
- `wab.py` (#100 п.6): комментарии о моменте сохранения намерения и о жизни ключа в полёте описывают фактическое
  поведение.
- Не исправлялось (#113 W3): фиксированный ответ с командой, которую отклонит `state.py` (`--accept` без findings на HEAD
  после `resume`, текст 1.4.3 без `--note`) — `state.py` падает закрыто и называет причину, решение уходит владельцу.

### Исправлено

- Решение по фиксированному ответу принимается по свежему состоянию (#100 пп.12, 14, 3): под замком ввода прямо перед
  вводом и перед Enter `fixed_answer` пересчитывается, и ответ уходит, только если ключ и текст те же; иначе в окно
  ничего не уходит, а эпизод получает отказ «состояние развилки изменилось после ввода ответа». Отказ записывается,
  только пока `status` читается как его строка: переписанный во время проверки `status` (в том числе пустой посреди
  перезаписи) не даёт ни отметки отказа, ни уведомления об уже кончившемся эпизоде.
- Отметки автоответов проверяются по полной схеме (#100 п.9): ключ развилки неверной длины или с полем не того типа,
  `policy_key_pending` без `status`/`text` — отказ «отметки автоответов в state.json испорчены», а не новый
  автоответ той же развилке.
- Причина отказа по испорченному контейнеру `attempts` называет `attempts`, а не `policy_keys / policy_key_pending`
  (#100 п.5).
- По ревью PR #115: фиксированный ответ проверяется ещё раз между вводом и Enter — устаревший к Enter текст не
  отправляется, строка ввода очищается, эпизод получает отказ; повторный пересчёт под замком перечитывает `status`,

  автоответов … испорчены», а не новый автоответ. Каждая команда фиксированного ответа исполнима: `--decision` с
  `--note`, `--accept` с `--source`, `--severity`, `--note`.
- `status` в `policy_episode` и `policy_refusal` — только eid строки: пустая или произвольная строка, короткий eid —
  испорченная отметка (отказ владельцу), а не «другой эпизод», который молча перезаписывается и даёт автоответ.
  Уточнение 1.5.3: для `policy_refusal` это верно только в памяти — миграция `load_state` до 1.5.3 превращала
  произвольную строку и короткий eid с диска в валидный eid; с 1.5.3 мигрирует только строка `BLOCKED` с валидной меткой.
  Пустой `status` старой отметки миграция больше не превращает в eid пустой строки (GitHub Codex на PR #115).
- Отказ политики, `cap reached` и их уведомление владельцу не пишутся, если волна ушла со строки, пока очищалась строка
  ввода с набранным ответом (отказ после проверки перед Enter, отказ по испорченной отметке, понижение капа):
  такт кончается без решения, следующий решает по свежему состоянию (Astra на PR #115, #100 п.12).
- Проверка перед Enter идёт перед КАЖДЫМ нажатием: если первый Enter не ушёл и `submit` повторяет его, повтор
  проверяется так же (и при первой доставке, и при повторе «только Enter»). Пересчёт под замком, давший то же
  решение, перечитывает `status` и ответ владельца после себя: кончившемуся эпизоду ответ не печатается. Ключ развилки

  волнами, получает свой Enter: повтор принимает формулировку 1.4.3 того же решения (ключ, вариант, прогон).
